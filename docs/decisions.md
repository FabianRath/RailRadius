# Decisions

Short log of notable choices, newest first. Format: date — decision — why.

- **2026-10-15 — Feed alerts (F29) are a daily email about the served store, with per-feed pauses that end when the data changes; the live server gets an admin token.** Email was chosen as the most reliable channel, so `spring-boot-starter-mail` was added (approved by the user); push via a webhook (ntfy, Discord) would have needed no dependency. The server has no zips (`HOSTING.md`), so how long each feed runs (`FeedTimespan`: calendar days and early-ending main operators) is computed on each load from the zips and stored in the binary cache (format version 2), and the alerts read that: they warn about the data actually served, not about a newer zip on the dev machine. The alert threshold is its own setting (`feeds.alerts.days`, 14) so the admin panel keeps marking feeds `EXPIRING` 30 days ahead. One mail lists every due feed; it goes out at a fixed time (cron, 08:00) instead of at startup, so restarts after each data upload don't send extra mails. Some feeds have been outdated for good (Bosnia, B36), so a feed can be paused; the pause stores the day its trains end and holds only while that is still the day, so new data that runs out again alerts again. On/off and the pauses live in a small JSON file next to the store rather than in config, so they survive restarts and change without a redeploy; alerts start off, so a server that isn't live sends nothing. Managing them in the admin panel means the live server needs `RAILRADIUS_ADMIN_TOKEN` set, which reverses the earlier plan to leave it unset there.
- **2026-10-15 — The "updating timetables" notice (F28) is frontend-only and reads the existing `/health`.** A reload clears the graph and the health turns DOWN; a restart makes the backend unreachable. Both read as "updating", so `/health` needs no new field (no public API change). The check runs only after something fails or a station search finds nothing, plus once on page load, so a healthy page sends no extra requests. A fresh instance without data also shows the notice, which fits: its timetables are about to be loaded. The page itself is served by the backend, so a visit while the backend is down gets no page at all; only a reverse proxy's error page could cover that.
- **2026-10-13 — MapLibre GL JS and Turf are copied into `frontend/vendor/` instead of loaded from unpkg (S29).** Every visit to a CDN sends the visitor's IP address to that third party, which German courts have ruled a GDPR breach without consent (LG München, 2022, on Google Fonts). Copying adds ~1.8 MB to the repo but no build step; upgrading means downloading the new files from the same npm package paths. MapLibre's ESM build is three files: `maplibre-gl.mjs` imports `maplibre-gl-shared.mjs` and starts `maplibre-gl-worker.mjs` from next to its own URL, so all three must stay together. The `.map` files are left out, so the browser devtools may log a missing source map.
- **2026-10-13 — The server is sized for the compact engine: 4 vCores, 8 GB, `-Xmx1280m`, still 2 permits (S25).** With 2 permits the heap settles at ~720 MB (279 MB idle, a ~170 MB scratch per permit, ~2 MB per stored result), and a burst of 8 large searches plus S15's load ran without a full GC at `-Xmx1280m`; `-Xmx1g` had one, `-Xmx768m` dozens (`HOSTING.md`). 4 permits needed ~1.5 GB and the burst finished no sooner, since each search already uses several cores. 4 GB RAM would hold the process (~1.5 GB working set); 4 vCores were picked over 2 because 5-transfer searches ran ~1.5× slower with 2 processors.
- **2026-10-13 — A search's minutes are chars and a station's boardings are released once ridden (S23 done); a large search holds ~195 MiB.** Trip progress, labels, rides and boardings keep durations as chars (`PackedMinutes`): with waits of at most 180 min a journey stays far below 65,534 min, and a longer one fails fast instead of wrapping, so results are exact. Scratch 183 → 171 MB. Boardings outside the scratch shrink by a sixth, stations that board nothing share empty arrays, and a station's boardings are dropped once ridden, since part of the peak falls while the round rides. Held (Stockholm, 5 transfers, fresh app) 207–223 → 192–194 MiB, zero diff, no slower. Tried and dropped: giving a trip progress slots only from its first boarded stop. 334 k trips are boarded earlier in a later round, so with a new block each time it would need 6.47 M slots instead of 2.93 M, and only 12 % of today's slots are never written. Grouped arrivals as ints were not tried: they would need a record → ride lookup per arrival.
- **2026-10-10 — The served stores and the dev/full goldens are a fresh parse of the zips with the B29/B30 merge rules (S26).** Until now `gtfs-store.bin` and `gtfs-dev-store.bin` came from the 2026-10-07 JSON caches, so measurements ran on the old station merges. Both stores are now parsed from the current zips; HEAD's `SearchSnapshot` on them is byte-identical to the S21 fresh-parse dumps, which became `data/snapshots/dev-2026-10-09.txt.gz` and `full-2026-10-09.txt.gz`. The older dumps and the old store were deleted; the JSON caches stay for the `pre-compact` rollback, whose jar does not need a binary store.
- **2026-10-10 — The scratch arrays grow by an eighth instead of by half, and the drop flags are bits (S23, partly done); a large search holds ~210 MB.** A scratch is reused and never shrinks, so spare room from growing is held for good, while growing again only happens until the scratch has seen the largest search: Stockholm's arena had 1.79 M places for 1.23 M labels, trip progress 3.78 M slots for 2.98 M. Growing by an eighth (`ScratchCapacity`) costs more copies on a fresh scratch only; no slower in `bench.sh times`. The drop flags (one byte per record, 5.9 M) became a `long[]` bitset; rides mark them in parallel and a word can hold two rides' records, so a ride ORs its bits in with one atomic `getAndBitwiseOr` per word. Scratch 218 → 182 MB, held 232 → 209–215 MB, zero diff.
- **2026-10-10 — A round's rides are kept as rows, and only the arrivals that become candidates or are boarded from get a label (S23, partly done); a large search holds ~250 MB.** Stockholm, 5 transfers: round 4 rides 1.25 M trips and makes 5.9 M arrivals, but only ~1.0 M of them are boarded from and ~0.13 M become candidates, and after the next trim ~0.1 M labels are left. So a ride is one row (board event, label boarded from, minutes and days at boarding, end of its records, 24 bytes) until the next round has boarded, and grouping works out each arrival's duration again from the trip's legs, with the same `TimetableStore.rideLegMinutes` riding uses. A grouped arrival packs ride, stop and minutes since boarding in a `long`. The arena peaks at 1.24 M labels instead of 6.97 M; scratch 360 → 218 MB, held 363–385 → 252 MB, zero diff, same speed. A candidate that is also boarded from gets a second, equal label: the result's journeys are the same, it grows by ~2 % (1.69 → 1.72 MB). Labelling the boarded-from arrivals one by one after the trim cost ~140 ms per large search (~6 % slower); each station now lists them once while it chooses, and stations label theirs in parallel into slots the arena reserves (~20 ms). Left of the 252 MB: trip progress 79 MB, labels 50 MB (1.24 M is just over the 1.20 M growth step), grouped arrivals 49 MB, rides 36 MB, ~42 MB of boardings outside the scratch.
- **2026-10-10 — A boarding whose ride can't record its trip's next stop is not boarded (S23, partly done); the scratch stays at ~360 MB.** Most rides of a large search record nothing: their first stop was reached no slower on all their days by an earlier round. Choosing a boarding now checks that stop against the trip progress as it stood before the round. Riding only lowers durations and adds days, so a stop that fails the check then also fails it when the ride comes, and dropping the boarding is exact: zero diff on gtfs-mini, dev and full data, and the same stop arrivals. The ride's label boarded from then needs no place in the trim either. Stockholm, 5 transfers: 21.5 M → 9.2 M boardings, at most 9.8 M → 3.5 M per round (~118 → ~42 MB held until ridden), labels kept by the round-5 trim 2.28 M → 1.0 M. 5-transfer p50 1.76 → 1.45 s, p95 2.72 → 2.29 s (`HOSTING.md`). The scratch did not shrink. The arena still peaks in round 4 at 1.09 M kept + 5.88 M new arrivals = 6.97 M labels, which needs the same 9.08 M capacity step (it grows by half) as the old 7.8 M did. ≤ 200 MB still needs fewer arrivals. A productive ride makes ~4.7 labels that share trip, board stop, previous and days, so storing those per ride could be the next step.

- **2026-10-10 — The legacy engine and the JSON cache are gone (S21); load-time trip data lives in a `RailNetwork` that is dropped after the store is built.** The tag `pre-compact` (4a01642) is the rollback: its jar runs from the JSON caches still on disk. Nothing reads JSON anymore, so a load of the zips writes only the binary cache, and the cache's header hash is now the SHA-256 of the zips (contents in file name order) instead of the JSON file. The station merging needs every trip's stops and connections and the edges, which the served graph doesn't, so they moved from `TransitGraph` to `RailNetwork`; `TransitGraph` is filled from the same `BinaryCacheData` whether it comes from the file or from a load, so a fresh load serves exactly what the next start reads. The graph's `neighbors` became `TimetableStore.nextStationCount`, derived on load like `evTrip` (same `/stats` and station search order, format version unchanged). `SearchEngine` and `SearchResult` had one implementation left and were folded into `CompactReachabilitySearch` and `CompactResult`; the `Compact` names stay. Gate: zero diff (S22 dumps reproduced from the S22 binary cache; S21 and S22 jars parsing the same zips give identical dumps). A fresh parse differs from the S22 goldens on dev and full data, because the JSON caches they came from (2026-10-07) predate the B29/B30 merge rules. Targets not met, as in S22: ~330 MB held per large 5-transfer search (≤ 200 MB needs fewer labels, see S22) and a 5-transfer p50 of 1.7 s (≤ 1.5 s); the rest is met (`HOSTING.md`). The legacy `TransferWindowTest` and the S17 store-vs-`SearchTimetables` comparison went with their classes; the merged-trips and B37 contract tests now run on the store.
- **2026-10-10 — The compact engine's memory (S22) is cut by trimming what each label and boarding stores, not by changing the round structure; a search still holds ~330 MB.** Held per large 5-transfer search on a fresh app 492–580 → 331 MB (Stockholm), scratch 447 → 360 MB, zero diff, same speed; 4 concurrent 5-transfer searches at `-Xmx3g` finish without a full GC and at `-Xmx2g` without running out of memory (`HOSTING.md`). What was done: a boarding is 3 ints (departure event with the overnight bit, label boarded from, minutes), its days are worked out again from the label when it is ridden; trip progress has slots only for the trips a search reaches; candidates link through a pool emptied after each round instead of a `next` int per label; a label's transfers are its chain length instead of a byte; the exact-days memo and its day shift are one packed int instead of int + byte. Overtaken arrivals are marked once in parallel instead of checked twice, which pays for the extra lookups. Tried and dropped, each made searches slower: storing a boarding in 2 ints and working out its minutes again too (4 more random label reads per boarding, ~8 %); the days memo as a hash side table, 24 instead of 28 bytes per label (choosing paths ~40 % slower, mid-size searches ~10 %). Not tried: riding each station batch right after choosing it, since the trim would then move after the round and the arena would hold the previous round's ~3 M unboarded arrivals more (≈ the boardings it saves); pruning arrivals no departure can use, since a 3 h wait window at a served station almost always finds one. S21's ≤ 200 MB per search would need fewer labels, not smaller ones.
- **2026-10-10 — An `OutOfMemoryError` in a stream's search ends the stream with an `error` event, and the failed search's scratch is dropped (B38).** Catching an `Error` is usually wrong, but here the failed search's memory is garbage once it has unwound and its gate permit is released by the `finally`, so the app is fine; without the catch the client waits forever. Only `OutOfMemoryError` is caught, at the SSE worker boundary. The scratch is dropped because the arena grows its columns one by one: an OOM halfway leaves columns of different lengths, and the next search on that scratch would fail with an index error. Other failures (a client that left: `CancellationException`) keep their scratch.
- **2026-10-10 — The binary cache (S20) holds only what the compact engine needs, and the graph restored from it has no trips.** The file has stations, translated names, each store trip's `TripInfo` and the `TimetableStore`, so the full data starts in ~3 s at 294 MB live (S19: 38 s, 1.54 GB), with a startup peak of 1.24 × live. The legacy engine searches the graph's trips, so it keeps loading the JSON cache and never writes or reads the binary one; that ends with S21. The graph's edges are the store's legs (equal to the JSON graph's: `/stats`, station search order, unit test), so `StationSearchIndex` and `/stats` work unchanged and the index needs nothing from `StationTable`, which lacks the names. `connectionCount()` became `edgeCount()`, which has the same value on a cache-loaded graph and needs no connections. The header's hash is the SHA-256 of the JSON cache the file was built from, logged on load to trace a server's file; it is not checked at startup, since a server has no JSON cache and hashing 650 MB would cost a second. "Version mismatch fails fast" means the reader rejects the file before reading a block; the app then logs it and uses the JSON cache, like a missing or truncated file. `regularDeparture` is stored (it needs `ServiceDays` unions per departure group), `evTrip` derived again (~10 ms). The file is read through one 1 MB direct buffer, not memory-mapped: on Windows a mapped file can't be replaced while the mapping lives, which would break the rewrite on reload. `TripInfo`s stay a map by trip ID in the graph, because `JourneyLegBuilder` looks them up by a connection's trip ID; 430k entries are part of the 294 MB.

- **2026-10-10 — Journeys and the result cache on the store (S19) are accepted without the gate's "4 concurrent searches at `-Xmx3g`", which moves to S22.** Zero diff on gtfs-mini, dev and full data on both engines, a stored 5-transfer result is ~2 MB (live heap growth 2 MB per result for Wien, Basel, München; S16: 32 MB) and the app starts at `-Xmx3g` in 39 s. Four concurrent 5-transfer searches at `-Xmx3g` ran out of memory: each needs a ~444 MB scratch over 1.54 GB idle, which is S22's work, not the result's. With the default 2 permits, 4 large searches at once (2 queued) finish fine at `-Xmx3g`. How it differs from the council's sketch: the chosen paths' labels survive the arena's round trims (one mark per chosen path, a few MB at most) and one last trim copies them out, instead of copying each round's chosen chains out with a remapping table; a `CompactResult` keeps trip, previous, duration, board/alight stop and transfers per label (17 bytes), not the days or the `WeekPeriodDays`; a cut-down result is a view on the stored arrays, not a copy. Re-running the search on a `/journey` miss is not needed, since results stay far under 5 MB. Connections are still built for a journey (`TimetableStore.legConnection`), because `JourneyLegBuilder` and the oracle work on them; the event-based `JourneyRunningDays.withRide` takes board and alight event only, the trip follows from the board event. Both engines answer through a temporary `SearchResult` interface, deleted with the legacy engine in S21.
- **2026-10-09 — The compact search engine (S18) is accepted at ~450 MB per large search, not the planned ≤ 200 MB; the rest of its gate is met.** Zero diff on gtfs-mini, dev and full data, the contract tests pass on both engines, and the 5-transfer p95 is 46–50 % of S16 (4 transfers 50–52 %). The council's ≤ 200 MB assumed far fewer rides: on the full data, rounds 3–5 of a big search each make 5–6 M arrivals that the next round boards from, plus up to 22 M boardings per search, and the semantics contract fixes that round structure. The scratch is reused per gate permit, so it is kept between searches. What brought it down from 1.2 GB: after a round's boardings are chosen the arena keeps only the labels later rounds reach (boarded from, and their earlier rides), the last round stores only candidates, and a station's sorted arrivals and windows live only while it chooses. Further cuts (riding station batches right after choosing, smaller labels, trip progress only for reached trips, maybe pruning dominated arrivals) are S22. Other differences from the council's sketch: exact days are worked out per transfer count in parallel, each label writing only its own slot, instead of a concurrent memo, and `arrSec` is not stored (it is the alight event's); a station's arrivals sort by arrival seconds then label, which is their arrival order, so the sort is stable for free; the store got `evTrip` (+23 MB), because looking up the trip of each scanned departure by binary search would cost seconds per search; the fallback scan skips blocks of 32 arrivals whose days can't help or whose latest start can't win (exact, small gain); paths are still built from `SearchTimetables`' `Connection`s, so results share them with the graph like the legacy ones (S19 changes the result type). The store is built at startup by `SearchEngine.prepare` only when the compact engine is on.

- **2026-10-09 — Stop IDs share the station's String, and the app runs with `-XX:+UseCompactObjectHeaders` (S16).** The JSON reader made a new String for every stop of every trip: 17 M Strings, a quarter of the full-data heap. Sharing the station's instance in `TransitGraph.restore` is a few lines, unlike `String.intern()` or `-XX:+UseStringDeduplication`, which work on every String in the JVM and, for G1's deduplication, only after objects survive several GCs, so the startup peak would stay. Compact object headers are a product flag since Java 25 and shrink every object by 4 bytes; the tens of millions of small objects make that worth it. Together: idle live heap 2,770 → 1,695 MB, same results, searches slightly faster (`docs/HOSTING.md`).
- **2026-10-09 — At most 2 searches run at once, 6 more may wait; the warmer only uses a free permit (S15).** A full-data 5-transfer search holds ~1 GB, so without a limit any heap size could run out (10-08 council). The gate sits in `ReachabilityCache`, the one place that starts a search, so stream, POST, `/journey` and warmer all count. The warmer never queues: it would double the load exactly when visitors wait. A queued stream sends an SSE comment every second to notice a closed tab; a running one notices at its next round's send, so a gone client can hold its permit for one more round. Busy uses the existing `error` event and 503 rather than a new "queued"/"busy" event, which would change the public API.
- **2026-10-08 — The server only answers searches, from a cache built on the dev machine, on 16 GB RAM with `-Xmx9g`.** Measured on the full data, the app needs ~3 GB for the data plus ~1 GB per 5-transfer search running at the same time; 5 GB of heap already ran out with three at once (`docs/HOSTING.md`). 32 GB plans had become scarce and expensive after the 2026 DRAM price increases. Parsing the zips needs less memory than searching, but it takes minutes and 3 GB of zips, so it stays on the dev machine and only the cache is uploaded.

- **2026-10-07 — Cross-border names are compared after transliteration, without words for "station", with typo tolerance, and a name contained in the other merges only within ~100 m (B29, B27).** About 30 stations stayed duplicated within 500 m, so their trains didn't connect (Sofia, Plovdiv, Bologna, Copenhagen, Split, Berlin Ostbahnhof). All 50 cross-feed pairs left within 500 m in the full cache of 2026-10-07 were checked by hand: the rules merge 27, all real duplicates, and none of the separate stations. Containment alone would also merge separate stations of one town, such as Cotral's "Viterbo" and Trenitalia's "Viterbo Porta Fiorentina" (126 m), so it needs ~100 m; real duplicates are mostly within 30 m. Typo tolerance requires the same first letter, because "Errenteria" and "Lezo-Rentería" are separate stations. "Centre" stays a real word: "Avignon Centre" and "Avignon-TGV" are different stations that one feed puts 33 m apart. A full reload confirmed it (34,187 → 34,156 stations, 50 → 25 pairs within 500 m). It also folds the SNCF feed's bus stops next to a station ("Valence Gare Routière", used by rail-replacement buses) into that station via the Swiss feed's copy, since "gare" is a generic word; that is the same place, so it stays. Still separate, because no general rule tells them apart from separate stations: Córdoba ("CORDOBA-CENTRAL" / "Córdoba-Julio Anguita"), Alicante, San Donà di Piave, Roissy CDG 2, Napoli Afragola (three names), Scalea and Spielfeld.
- **2026-10-07 — Feed credentials live in local settings, referenced from `gtfs-feeds.txt` as `${setting}` in a header; extra TLS roots for feed hosts are bundled in `feed-roots.pem` (B36, Hungary).** MÁV's feed needs HTTP Basic auth with a personal account, which must not be in git. A placeholder keeps the URL list in one file and works with any header, and Spring's environment already reads env vars and a gitignored `backend/config/application.yml`; it is resolved only at download time, so the app starts without it and the admin API never sees it. The setting holds the ready base64 value, not user and password, to avoid special auth syntax in the feed file. MÁV's certificate chains to Microsec e-Szigno Root CA 2009, which Windows and Mozilla trust but the JDK doesn't ship. Bundling that public root and trusting it only in the feed downloader's `HttpClient` works on every machine; switching the JVM to the Windows trust store (`-Djavax.net.ssl.trustStoreType=Windows-ROOT`) would be Windows-only and change TLS for the whole app.
- **2026-10-05 — A feed can list fallback URLs, tried in order when a download fails or is rejected.** `s3.transitpdf.com`, the source of ten feeds, stopped resolving (the files moved to `blues3.transitpdf.com`), and France's URL started serving a feed without rail routes, so single URLs proved fragile. A fallback is a repeated line in `gtfs-feeds.txt`, not a second field, so each URL keeps its own headers. A rejected download (expired, too small, no rail routes) falls back too, not only an HTTP or network error, because a stale or broken primary is exactly when a mirror helps. The checks against the current zip still apply to a fallback, so one that serves a different or smaller feed is only taken if it is not much smaller. The API still reports only the first URL (`FeedStatus.downloadUrl`); the download result names the host the zip came from.
- **2026-10-05 — A downloaded feed must also have rail routes, service days, at least half the current zip's size and run today.** These catch a URL that now serves a bus-only or different feed, a truncated export, and a feed without a calendar (the loader would run all its trips every day and the update center could not tell when it expires). A real update rarely shrinks by half, so 50 % is loose enough not to block normal timetable changes. A feed that only starts later is rejected because it would leave no trains for today; download it again once it runs.
- **2026-10-05 — Feeds are kept current by an admin update center that downloads on request, without reloading by itself (B24).** Nine feeds had expired without anyone noticing, and since B25 an expired feed also stops trains from connecting at transfers. The update center shows how long each zip runs, logs expired and expiring ones at startup and once a day, and downloads a new version of a feed from `gtfs-feeds.txt` on request. It does not reload: on full data a reload takes minutes and 12 GB of heap, and searches fail while it runs, so you decide when. It doesn't download on a schedule either: a source that goes stale or changes format should be looked at, not swapped in unattended. Validity comes from the whole feed's calendar, not only its rail services, so a zip can be checked without parsing trips.txt and before it is loaded. In mixed feeds this can be a little later than the end of the rail services. A download replaces the zip only if it is a GTFS zip, has not expired and doesn't end earlier than the current one, because a portal that serves an HTML error page or an old file must not destroy a working feed. The replaced zip is kept in `previous/` (one generation), since a bad feed often only shows after the reload. URLs live in `gtfs-feeds.txt` and no longer in `gtfs-sources.md`, so the code reads them from one place. Feeds without a direct download (login, fee, web page) are not listed and are updated by hand.
- **2026-10-05 — UI icons are Lucide SVGs copied into `js/icons.js`, not emojis or an icon library.** Emojis look different on every OS and can't take the CSS colour variables. The UI needs about ten icons, so a CDN icon font or script (hundreds of KB, another runtime dependency) isn't worth it. Lucide is ISC (a few icons MIT, from Feather), which allows commercial use as long as the licence notice stays in the copy, so it is in the file header. The SVGs draw in `currentColor`. Alternatives considered: Tabler, Phosphor, Bootstrap Icons (MIT webfonts), Material Symbols (Apache 2.0); Font Awesome Free needs attribution, Heroicons has no train.

- **2026-10-05 — Journeys show the weekdays they run on, not dates (F14).** The search has no travel date (B25), and a journey usually runs on many days, so a single date would be an arbitrary pick, and it would be wrong for journeys whose trains never all run on one day: B25 only checks consecutive trains. Date ranges were dropped too: they mostly show feed validity, which isn't what the popup is for. The days are the intersection of every trip's `ServiceDays`, computed after the search for the returned journeys only, so the search costs nothing more. Weekdays count when the journey runs on at least half of their dates, so a holiday doesn't turn "Mon–Fri" into a list. Journeys whose trains share no day are flagged in the popup, not hidden: hiding them would need the whole-chain check B25 decided against. Feeds publish one train as several trips with the same times but different days (NS train 9535: 7 trips, one with 4 days, differing in one intermediate stop ID), and the search keeps only one of them, so a ride's days are the union over all trips with its departure and arrival times between the same two stations. That matches by times, not train number, since two trips with the same times between the same stations are the same ride for the passenger.
- **2026-10-05 — A feed's own category column is configured per source, not read wherever it exists (F15).** The Netherlands keep the category in `trip_long_name` (Sprinter, Intercity, ICE, Eurostar…), Poland in `plk_category_code` (Os, R, IC, EIP, TLK…). Estonia also has `trip_long_name`, but there it names the route ("Tallinn - Keila"), so the column means different things in different feeds. `train-category-columns.txt` lists source and column, next to F16's `train-categories.txt`, so a new feed needs no code. The column's value goes in front of any train number, not only a bare one, because Polish numbers carry the train name ("1900/1 Zosia" → "IC 1900/1 Zosia"). It wins over a route-type rule because it is per trip. For Polish regional trains this replaces the operator code the popup used to show ("AR 50324" → "Os 50324"). Cache format 8.

- **2026-10-05 — Service days are checked per transfer, without a travel date (B25).** The app is a general overview of possible connections, not a planner for one day, so the API stays dateless. A transfer needs the arriving and the departing train to share a day (the next day for a wait past midnight); the whole journey is not checked, so A→B→C can pass when A and B share one day and B and C another. Checking the whole chain would need each ride to carry its set of possible start dates, and pruning to keep rides whose date sets differ, which costs search time and memory. Days are a bitset over epoch days per service, shared by all its trips (cache format 7). When the window's best arrival fails the check, the arrivals in the wait range are scanned, so the result is still the best passing arrival. Trips without a calendar entry run every day. Consequence: feeds whose validity periods don't overlap no longer connect (B24). On dev data the Hungarian feed ends on 2025-11-23 and the Austrian/Slovak ones start on 2025-12-14, so Wien Hbf with 5 transfers drops from 2,996 to 1,907 stations. Budapest-Keleti still reaches 2,996, because round 0 boards ÖBB trains from the Austrian feed there. Search time on dev data with 5 transfers: 0.6–1.3 s (was 0.8 s).

- **2026-10-05 — German long-distance categories (ICE/IC/ECE) are derived from the route type, as Transitous does (F16).** The DELFI feed names DB Fernverkehr routes by line only (`33`) and gives bare train numbers, so the category passengers see is only in `route_type` (101 high-speed, 102 long-distance). gtfs.de's free feed has the categories but no train numbers, and its paid plans don't say whether they add them (see `gtfs-sources.md`). Transitous applies 101 → ICE, 102 → IC, ECE for lines 20/75/85/88; we copy that in `train-categories.txt` (rules per source and agency) instead of hardcoding it, and the gtfs.de route list (`ICE 33`, `IC 33`, `ECE 85`…) agrees. A wrong label is possible where DB runs a line with the other train type; revisit if a feed with real categories and numbers turns up.
- **2026-10-05 — Train number, headsign and operator are stored per trip (`TripInfo`), not per connection (F13).** A connection exists per stop pair, so per-connection fields would multiply the memory and cache size by the stops per trip. Only rail trips are kept from trips.txt, which also shrinks the old trip→route map. Numeric `trip_short_name`s lose their leading zeros, because the German feed pads them ("002310") and bahn.de shows "2310". The popup decides how to combine route name and train number, since feeds split them differently ("Ex 42" + "42", "ICE" + "2", "A10-1" + "RJ 658", "33" + "2310"). Cache format 5, so existing caches are re-parsed.
- **2026-10-04 — Cross-border stations with different names are matched by shared trains and by country borders, not by a larger radius (B22).** Feeds often name a border station in their own language ("Aachen, West Bf" / "Aix-la-Chapelle Ouest", ~135 m apart), so the word-overlap check fails, and a wider name-free radius risks merging different stations. Instead: (1) a cross-border train is in both feeds, so ≥ 3 trains at the same minute with the same neighbour station mark one station; (2) a stop outside its feed's home country is a station that country's feed has too, so it snaps to the nearest one within 1 km. Borders: Natural Earth 1:10m admin-0 countries (public domain), cut to Europe, coordinates rounded to 4 decimals, only an `iso` property (`ISO_A2_EH`, because `ISO_A2` is -99 for France and Norway): `backend/src/main/resources/borders/europe.geojson`, 1.8 MB. The cost is many short, frequent trips (memory, search time). It was not measured: the dev data has no type-109 routes. An existing full-data GTFS cache keeps the old trips until it is re-parsed.

- **2026-10-04 — Reachability is a round-based search with per-trip pruning; the incremental BFS is gone (B2, B3, B4, B21).** The old BFS kept one path per station, ranked by (transfers, duration), and let the first path to reach a `station|trip|transfers` boarding claim it. Arrival time was ignored, so a faster path that arrived too late for the next train hid a slower one that caught it. Results depended on the wait window in ways that made no sense: on dev data Wien Hbf with a 5 min minimum reached more stations at 4 transfers than with 0 min. Now one round runs per transfer count. Each trip keeps the shortest duration per stop, which is exact because two rides of the same trip at the same stop differ only in transfers and duration. Each departure is boarded once per station and round, from the arrival that catches it with the shortest journey, so a round costs about arrivals + departures, not their product. Boarding from every arrival was exact too, but took 20 s for 5 transfers on dev data and 60 s with no wait limit; the sweep needs ≤ 0.8 s and finds the same stations. Each station keeps the best path per transfer count, so the max-journey-time filter can fall back to a faster path with more transfers (B4), and a result with N transfers is a subset of one with N+k. That replaces the incremental N−1 → N search, which could not be exact without storing the whole search state. The warmer now searches only the maximum count. Dev data, 5 transfers, 0–180 min: Wien Hbf 2,716 → 3,090 stations, Budapest-Keleti 2,888 → 3,090, Bratislava 2,719 → 3,090. Feasibility of a wait is now compared in seconds, no longer in truncated minutes; this only differs for feeds with non-zero seconds.

The default budget (200, refilling 1/s) allows three fresh 5-transfer searches at once, then about one a minute, or a 2-transfer search every 5 s. The admin must never be limited, but the browser's `EventSource` cannot send the `X-Admin-Token` header, and a token in the query string would land in access logs. So dev login sets an HttpOnly, SameSite=Strict cookie holding the token, sent only to `/api/reachability/**`. Admin endpoints keep accepting only the header, so the cookie cannot be abused by a forged cross-site request. A search turned away by the gate (503) after being charged is not refunded: it is rare and costs at most one 5-transfer search.
- **2026-10-15 — The example search (F27) is Krems Bahnhof at 1 transfer, pre-filled but not run.** A small station keeps the first map uncluttered: ~300 stations at 1 transfer on the dev data, against ~2,900 for Innsbruck and ~4,900 for Linz. Running it on load would cost a search for every visitor and draw a map before they asked for one. It is looked up by exact name, since stop IDs can change between feed versions; if no station has that name, nothing is pre-filled.

- **2026-10-16 — The "Abfahrt" redesign self-hosts two web fonts, Barlow Semi Condensed and Doto (F33).** Barlow Semi Condensed gives the condensed departure-board look and stays readable at small UI sizes; Doto is a dot-matrix face used only for board numerals (digits and `:`), so only its latin file ships. Both are woff2 files in `frontend/vendor/fonts/`, never loaded from Google at runtime, for the same GDPR reason as S29 and S31. Barlow ships latin-ext as well because station names contain ł, ř, ő, ş and the like; the vietnamese subset is left out. Both are SIL OFL 1.1, which allows commercial use and self-hosting as long as the licence ships with the files (`OFL-BarlowSemiCondensed.txt`, `OFL-Doto.txt` next to them). This replaces S31's system fonts for the UI; the mono stack stays a system stack.
- **2026-10-16 — The side panel's collapse toggle is gone, not replaced (F35).** With the search in a bar across the top, the map has the full width whenever no journey is open, and the journey column has its own close button. Opening or closing the column calls `map.resize()` at once (`resizeMap()`) instead of waiting for MapLibre's ResizeObserver, and keeps the map's centre rather than refitting, as before.
- **2026-10-17 — Search requests are bounded and rejected outside the bounds, not clamped (B41, B42).** The rate limit charges by transfer count only, but a long wait window makes a search many times slower (1440 min: ~7× on dev), and every distinct parameter set is its own entry in the 30-entry result cache, so made-up values could hold the search permits at a low price or push real results out (an unknown station cost 1 and was stored too). Waits at changes are capped at 360 min: 6 h covers any sensible change, and the UI used to allow 9999 and sent 99999 with the limit switched off. A clamp would still turn each made-up value into a new cache key and hide client bugs, so out-of-range values get a 400 (an SSE `error` event on the stream) naming the bound; the frontend clamps its fields to the same bounds, so a normal visitor never sees it. "Limit wait at changes" off now means 0–360 min, and the Wait cell says "max 6h" instead of "off" so the cap is visible. The overnight-window test needs waits up to 24 h, so it calls `CompactReachabilitySearch` directly; the B4 tests' fixture train X4 moved from 22:00 to 15:00, a 4.5 h wait.
- **2026-10-17 — The first view is fitted from a country bounding-box table in the frontend, not from coordinates in `/api/coverage` (F47).** `/api/coverage` returns only ISO codes, and adding bounds to it would change the public API for a purely visual need. The backend can only report the codes in `borders/europe.geojson`, so `js/country-bounds.js` lists an approximate mainland box for each of those (remote islands without rail left out, so they don't zoom the map out); an unknown code is ignored and keeps the all-of-Europe default. The request runs alongside the map load and the fit jumps without animation, so the page never waits for it.
- **2026-10-17 — Deep links replace the URL, name the station by stop ID, and leave default options out (F46).** Each search calls `history.replaceState`, not `pushState`: the URL always shows the last search that ran, and Back leaves the page instead of stepping through searches, which the page could not replay without re-running them. The station is its canonical stop ID (`from`), since names are not unique; an ID that changes with a feed version breaks the link, which then says so and falls back to the example station. `transfers` is always written so a link says how far it reaches; `hours`, `minwait` and `maxwait` only when they differ from the untouched form, to keep links short (a changed default changes what such a link searches). Colons in stop IDs stay unencoded for readability. Link values go through the form's own clamping, so they can't send what the backend rejects (B41) apart from a minimum wait above the maximum, which the form allows too. "Limit wait at changes" off is written as its range (`minwait=0&maxwait=360`) and comes back with the switch on, which searches the same.
