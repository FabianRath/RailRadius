# Decisions

Short log of notable choices, newest first. Format: date — decision — why.

- **2026-10-05 — A feed can list fallback URLs, tried in order when a download fails or is rejected.** `s3.transitpdf.com`, the source of ten feeds, stopped resolving (the files moved to `blues3.transitpdf.com`), and France's URL started serving a feed without rail routes, so single URLs proved fragile. A fallback is a repeated line in `gtfs-feeds.txt`, not a second field, so each URL keeps its own headers. A rejected download (expired, too small, no rail routes) falls back too, not only an HTTP or network error, because a stale or broken primary is exactly when a mirror helps. The checks against the current zip still apply to a fallback, so one that serves a different or smaller feed is only taken if it is not much smaller. The API still reports only the first URL (`FeedStatus.downloadUrl`); the download result names the host the zip came from.
- **2026-10-05 — A downloaded feed must also have rail routes, service days, at least half the current zip's size and run today.** These catch a URL that now serves a bus-only or different feed, a truncated export, and a feed without a calendar (the loader would run all its trips every day and the update center could not tell when it expires). A real update rarely shrinks by half, so 50 % is loose enough not to block normal timetable changes. A feed that only starts later is rejected because it would leave no trains for today; download it again once it runs.
- **2026-10-05 — Feeds are kept current by an admin update center that downloads on request, without reloading by itself (B24).** Nine feeds had expired without anyone noticing, and since B25 an expired feed also stops trains from connecting at transfers. The update center shows how long each zip runs, logs expired and expiring ones at startup and once a day, and downloads a new version of a feed from `gtfs-feeds.txt` on request. It does not reload: on full data a reload takes minutes and 12 GB of heap, and searches fail while it runs, so you decide when. It doesn't download on a schedule either: a source that goes stale or changes format should be looked at, not swapped in unattended. Validity comes from the whole feed's calendar, not only its rail services, so a zip can be checked without parsing trips.txt and before it is loaded. In mixed feeds this can be a little later than the end of the rail services. A download replaces the zip only if it is a GTFS zip, has not expired and doesn't end earlier than the current one, because a portal that serves an HTML error page or an old file must not destroy a working feed. The replaced zip is kept in `previous/` (one generation), since a bad feed often only shows after the reload. URLs live in `gtfs-feeds.txt` and no longer in `gtfs-sources.md`, so the code reads them from one place. Feeds without a direct download (login, fee, web page) are not listed and are updated by hand.
- **2026-10-05 — UI icons are Lucide SVGs copied into `js/icons.js`, not emojis or an icon library.** Emojis look different on every OS and can't take the CSS colour variables. The UI needs about ten icons, so a CDN icon font or script (hundreds of KB, another runtime dependency) isn't worth it. Lucide is ISC (a few icons MIT, from Feather), which allows commercial use as long as the licence notice stays in the copy, so it is in the file header. The SVGs draw in `currentColor`. Alternatives considered: Tabler, Phosphor, Bootstrap Icons (MIT webfonts), Material Symbols (Apache 2.0); Font Awesome Free needs attribution, Heroicons has no train.

- **2026-10-05 — Journeys show the weekdays they run on, not dates (F14).** The search has no travel date (B25), and a journey usually runs on many days, so a single date would be an arbitrary pick, and it would be wrong for journeys whose trains never all run on one day: B25 only checks consecutive trains. Date ranges were dropped too: they mostly show feed validity, which isn't what the popup is for. The days are the intersection of every trip's `ServiceDays`, computed after the search for the returned journeys only, so the search costs nothing more. Weekdays count when the journey runs on at least half of their dates, so a holiday doesn't turn "Mon–Fri" into a list. Journeys whose trains share no day are flagged in the popup, not hidden: hiding them would need the whole-chain check B25 decided against. Feeds publish one train as several trips with the same times but different days (NS train 9535: 7 trips, one with 4 days, differing in one intermediate stop ID), and the search keeps only one of them, so a ride's days are the union over all trips with its departure and arrival times between the same two stations. That matches by times, not train number, since two trips with the same times between the same stations are the same ride for the passenger.
- **2026-10-05 — A feed's own category column is configured per source, not read wherever it exists (F15).** The Netherlands keep the category in `trip_long_name` (Sprinter, Intercity, ICE, Eurostar…), Poland in `plk_category_code` (Os, R, IC, EIP, TLK…). Estonia also has `trip_long_name`, but there it names the route ("Tallinn - Keila"), so the column means different things in different feeds. `train-category-columns.txt` lists source and column, next to F16's `train-categories.txt`, so a new feed needs no code. The column's value goes in front of any train number, not only a bare one, because Polish numbers carry the train name ("1900/1 Zosia" → "IC 1900/1 Zosia"). It wins over a route-type rule because it is per trip. For Polish regional trains this replaces the operator code the popup used to show ("AR 50324" → "Os 50324"). Cache format 8.

- **2026-10-05 — Service days are checked per transfer, without a travel date (B25).** The app is a general overview of possible connections, not a planner for one day, so the API stays dateless. A transfer needs the arriving and the departing train to share a day (the next day for a wait past midnight); the whole journey is not checked, so A→B→C can pass when A and B share one day and B and C another. Checking the whole chain would need each ride to carry its set of possible start dates, and pruning to keep rides whose date sets differ, which costs search time and memory. Days are a bitset over epoch days per service, shared by all its trips (cache format 7). When the window's best arrival fails the check, the arrivals in the wait range are scanned, so the result is still the best passing arrival. Trips without a calendar entry run every day. Consequence: feeds whose validity periods don't overlap no longer connect (B24). On dev data the Hungarian feed ends on 2025-11-23 and the Austrian/Slovak ones start on 2025-12-14, so Wien Hbf with 5 transfers drops from 2,996 to 1,907 stations. Budapest-Keleti still reaches 2,996, because round 0 boards ÖBB trains from the Austrian feed there. Search time on dev data with 5 transfers: 0.6–1.3 s (was 0.8 s).

- **2026-10-05 — German long-distance categories (ICE/IC/ECE) are derived from the route type, as Transitous does (F16).** The DELFI feed names DB Fernverkehr routes by line only (`33`) and gives bare train numbers, so the category passengers see is only in `route_type` (101 high-speed, 102 long-distance). gtfs.de's free feed has the categories but no train numbers, and its paid plans don't say whether they add them (see `gtfs-sources.md`). Transitous applies 101 → ICE, 102 → IC, ECE for lines 20/75/85/88; we copy that in `train-categories.txt` (rules per source and agency) instead of hardcoding it, and the gtfs.de route list (`ICE 33`, `IC 33`, `ECE 85`…) agrees. A wrong label is possible where DB runs a line with the other train type; revisit if a feed with real categories and numbers turns up.
- **2026-10-05 — Train number, headsign and operator are stored per trip (`TripInfo`), not per connection (F13).** A connection exists per stop pair, so per-connection fields would multiply the memory and cache size by the stops per trip. Only rail trips are kept from trips.txt, which also shrinks the old trip→route map. Numeric `trip_short_name`s lose their leading zeros, because the German feed pads them ("002310") and bahn.de shows "2310". The popup decides how to combine route name and train number, since feeds split them differently ("Ex 42" + "42", "ICE" + "2", "A10-1" + "RJ 658", "33" + "2310"). Cache format 5, so existing caches are re-parsed.
- **2026-10-04 — Cross-border stations with different names are matched by shared trains and by country borders, not by a larger radius (B22).** Feeds often name a border station in their own language ("Aachen, West Bf" / "Aix-la-Chapelle Ouest", ~135 m apart), so the word-overlap check fails, and a wider name-free radius risks merging different stations. Instead: (1) a cross-border train is in both feeds, so ≥ 3 trains at the same minute with the same neighbour station mark one station; (2) a stop outside its feed's home country is a station that country's feed has too, so it snaps to the nearest one within 1 km. Borders: Natural Earth 1:10m admin-0 countries (public domain), cut to Europe, coordinates rounded to 4 decimals, only an `iso` property (`ISO_A2_EH`, because `ISO_A2` is -99 for France and Norway): `backend/src/main/resources/borders/europe.geojson`, 1.8 MB. Home countries are derived from where a feed's stations lie, so no per-feed config is needed. Tried first and reverted: merging any two stations within ~100 m, which missed Aachen (135 m).
- **2026-10-04 — S-Bahn routes (type 109) count as rail; 107 (tourist/heritage) still does not (B6).** 3,571 stops were served only by type 109 (Germany 3,260, Finland 238, Denmark 73), and S-Bahn trips through stations already in the graph were dropped as well, so much of the regional network was missing. The cost is many short, frequent trips (memory, search time). It was not measured: the dev data has no type-109 routes. An existing full-data GTFS cache keeps the old trips until it is re-parsed.

- **2026-10-04 — Reachability is a round-based search with per-trip pruning; the incremental BFS is gone (B2, B3, B4, B21).** The old BFS kept one path per station, ranked by (transfers, duration), and let the first path to reach a `station|trip|transfers` boarding claim it. Arrival time was ignored, so a faster path that arrived too late for the next train hid a slower one that caught it. Results depended on the wait window in ways that made no sense: on dev data Wien Hbf with a 5 min minimum reached more stations at 4 transfers than with 0 min. Now one round runs per transfer count. Each trip keeps the shortest duration per stop, which is exact because two rides of the same trip at the same stop differ only in transfers and duration. Each departure is boarded once per station and round, from the arrival that catches it with the shortest journey, so a round costs about arrivals + departures, not their product. Boarding from every arrival was exact too, but took 20 s for 5 transfers on dev data and 60 s with no wait limit; the sweep needs ≤ 0.8 s and finds the same stations. Each station keeps the best path per transfer count, so the max-journey-time filter can fall back to a faster path with more transfers (B4), and a result with N transfers is a subset of one with N+k. That replaces the incremental N−1 → N search, which could not be exact without storing the whole search state. The warmer now searches only the maximum count. Dev data, 5 transfers, 0–180 min: Wien Hbf 2,716 → 3,090 stations, Budapest-Keleti 2,888 → 3,090, Bratislava 2,719 → 3,090. Feasibility of a wait is now compared in seconds, no longer in truncated minutes; this only differs for feeds with non-zero seconds.

- **2026-10-04 — Station merge chains are resolved before merging, not prevented (B19).** The deduplicator can merge a station that is already the canonical of an earlier merge (a within-country pair's survivor merged across a border). Skipping those merges would leave real duplicates; `TransitGraph.mergeStations` instead maps every alias to the end of its chain first, since each remap step only resolves one hop. Chains can't form cycles: a merge target is never an alias at the time it is chosen.
- **2026-10-04 — stop_times batches are cut at trip boundaries; ungrouped files switch batching off (B17).** GTFS doesn't require stop_times.txt to be grouped by trip, and a trip split across batches had its stop list overwritten by its second part. Merging parts later would need each built trip's stop sequences and boundary times kept around; a second pass to count rows per trip would double the parse time of the largest file. Real feeds are grouped, and an ungrouped one shows it within the first batch, so after a repeated trip the rest of the file is read in one batch (memory instead of correctness). Rows that still arrive for an already built trip are dropped with a WARN, so the trip's stop list and connections stay consistent. `railreach.gtfs.trip-batch-size` exists so tests can use tiny batches.
- **2026-10-04 — The raw reachability cache holds at most 30 results and is cleared on reload (B9).** A full-data result maps up to ~17k stations to a `JourneyPath` each, so an unbounded map grew with every distinct query and warming adds up to five per query. Caffeine evicts by size (no TTL: results only go stale on reload, which now clears both the raw and the response cache). An evicted N−1 result only costs a full BFS for N instead of an incremental one. `GtfsDataService` calls `ReachabilityCache.clear()` directly; an application event would decouple them, but there is only one listener.
- **2026-10-03 — Reachability queries no longer use hub routing (B20).** `queryViaHubs` searched from the start with N−1 transfers and then allowed the last transfer only at one of the 50 hubs, checking a single arrival/departure pair there. The full BFS can change trains at any station, so hub results were always a subset (full data, Hatvan, 1 transfer: 140 instead of 782 stations), and the loss carried into N+1 via the incremental search. The full BFS for that query takes 0.7 s. The hub precompute, its cache file and its admin endpoints were removed on 2026-10-04 (B5 went with them).
- **2026-10-03 — The GTFS cache stores trips, not the derived maps (S9).** Measured on dev data, `connectionInfo` was 83 % of the file: ~350 bytes per connection, mostly repeated keys, trip/route IDs, the stop IDs already in the edge key, string copies of the times, and pretty-printing. The file now holds stations plus one `CachedTrip` per trip (route name, stop IDs, per-leg dep/arr seconds) as compact JSON; edges, connections and the stop→trips index are rebuilt on load through `addTrip`/`addConnection`. Full data: 3.6 GB → 357 MB, load 17 s; dev: 124 MB → 11 MB. Reachability results are identical to a freshly parsed graph. Times are stored per leg, not per stop, so legs the loader skipped (stop missing from stops.txt, or both ends merged) stay absent. Connections that match no leg of their trip (B19) are left out with a WARN count; the BFS walks stop lists and never reaches them. A `formatVersion` field makes old files be ignored with a warning and re-parsed. The dead `Connection.routeId`/`stopsApart` fields were removed.
- **2026-10-03 — Only stops used by a rail trip become stations (B18).** The loader builds all of a feed's stations first (same-name merging needs every stop), but adds one to the graph only when a rail trip uses it. Unserved parent stations and entrances are not kept. (Since B23, a served platform is merged into its parent, so the parent becomes the station.) Before this, ~97 % of stations had no edges.
- **2026-10-03 — `ReachabilityService` split up (S2), which fixes B7.** BFS (`ReachabilitySearch`), raw result store (`ReachabilityCache`), warming (`ReachabilityWarmer`) and DTO/leg mapping (`JourneyLegBuilder`) are separate beans. `HubRoutingService` now depends on `ReachabilitySearch` only, so the `ServiceConfig`/`@Lazy` cycle breaker is gone. Warming is its own bean so `@Async` goes through the proxy and runs off the SSE thread. It fills only the raw cache: the frontend only uses the stream, which never reads the Caffeine response cache, so warming the Caffeine cache bought nothing. The full BFS no longer enqueues stations that are already at the transfer limit; from there only the same trip could continue, and the ride that reached them already covered that trip. A comparison against the old code on the dev data gave identical paths.
- **2026-10-03 — `GtfsDataService` split up (S1); readers inject `TransitGraph`.** Loading (`GtfsFeedLoader`), station merging (`StationDeduplicator`) and the cache file (`GtfsCacheStore`) are separate classes, and `GtfsDataService` only orchestrates startup and reload. The data and its query API live in the `TransitGraph` bean, which the BFS, hubs and controllers use directly, so no service has to forward a dozen getters. `HubRoutingService` is `@DependsOn("gtfsDataService")`, because it no longer injects it but must start after the graph is filled. `GtfsCacheData` field names are the on-disk format and were kept, so existing caches still load.
- **2026-10-03 — Removed gtfs-lib; the JSON caches use Jackson 3 (S3).** Only its `Stop`/`StopTime` POJOs were used, now private records in the loader. It was also the only source of Jackson 2 on the classpath, so the cache code moved to Spring Boot's Jackson 3 (`tools.jackson.databind.ObjectMapper`). Existing cache files still load: Jackson 3 ignores unknown properties (the removed `intermediateStops`) by default.
- **2026-10-03 — The reachability SSE stream sends the finished result, not stations as the BFS finds them (B16).** The BFS improves a station's path several times during the search, so live emission sent duplicates and non-final paths, and the first run differed from cached repeats. Cache hits, incremental and hub-routed queries already only streamed after computing. The cost is that a slow full BFS shows nothing until it is done. The start station is never streamed.
- **2026-10-03 — Target Java 25 (LTS) and enable virtual threads.** With the full dataset (12 GB heap, millions of small objects) we can use compact object headers and generational ZGC. SSE streams now run on Spring's task executor (virtual threads) instead of a hand-made cached thread pool. Lombok 1.18.42 prints a harmless `sun.misc.Unsafe` deprecation warning on JDK 25.
- **2026-10-03 — Coding guidelines in `docs/CODING_GUIDELINES.md`, imported into CLAUDE.md via `@`.** The import loads them into every Claude session automatically. The dependency list is closed and shared logic has one named home, to stop style drift and copy-paste duplication (time helpers already exist 4×). Existing code is migrated as it is touched, not in one big rewrite.
- **2026-10-03 — Monorepo at `RailReach/`** with `backend/` and `frontend/`. Claude (and you) can see both sides of the API in one session.
- **2026-10-03 — All large data lives in `backend/data/` and is gitignored.** This covers GTFS zips and `gtfs-cache.json` (~4 GB). It keeps the repo small and keeps tools from scanning multi-GB files. Download sources are versioned in `docs/gtfs-sources.md`.
- **2026-10-03 — `dev` profile uses Austria + Hungary + Slovakia** (~8 MB of feeds in `data/gtfs-dev/`). It's small enough to start fast, and the three countries share border stations, so cross-border merging gets exercised.
- **2026-10-03 — Tests use a hand-written `gtfs-mini` fixture** (`src/test/resources/gtfs-mini/`), zipped on the fly by `GtfsTestFixtures`. Tests run in milliseconds and every expected value can be checked by hand. The Spring context test runs with profile `test`, which loads no data.
- **2026-10-03 — Known bugs are captured as `@Disabled` tests** with the reason in the annotation. Re-enable the test when fixing the bug.
- **2026-10-03 — Source files moved into folders matching their declared packages** (`controller`, `service`, `dto`, `model`, `config`). Before this, the files sat in one flat folder.
- **2026-10-03 — Base map: OpenFreeMap "dark" vector style, rendered with MapLibre GL JS 6 (replaces Leaflet).** We need a dark map that is free also for commercial use, with no key. CARTO now needs a key and is paid commercially. Esri's free tiles forbid commercial use. Stadia/MapTiler/Thunderforest free tiers are non-commercial. OSM's own tiles forbid heavy use and block requests without a Referer. OpenFreeMap has no key, no limits and allows commercial use, but it is a donation-funded single-maintainer service without an SLA. Fallback: self-host OpenFreeMap (MIT) or a Protomaps PMTiles file; both use the same MapLibre setup, so only `MAP_STYLE_URL` changes. Railway layers are recoloured and shown from z8 (the lowest zoom at which OpenFreeMap tiles contain railways), because rail is what the app is about.
- **2026-10-03 — The backend serves the frontend** (`spring.web.resources.static-locations: file:../frontend/`, `no-cache`). ES modules don't load from `file://`, the API is same-origin (`API_BASE = ''`), and edits show on reload without a rebuild.
- **2026-10-03 — Frontend split into `index.html` + `css/app.css` + `js/` ES modules.** The single 1,600-line file mixed markup, styles and logic. Still vanilla with no build step.
- **2026-10-04 — Admin API guarded by one shared token (`X-Admin-Token`), not Clerk/OIDC or Spring Security (F6).** Only the developer needs access (debug overlay, later an admin view for cache rebuilds); public users need no accounts. A Spring MVC interceptor with a constant-time compare needs no new dependency, while Clerk adds a paid external service plus a JS SDK and JWT validation, and Spring Security adds a dependency and filter-chain config for a single user. Locked by default: no configured token means 403 for every admin call. Revisit if several admins need their own logins, revocation or an audit trail. Requires HTTPS when deployed, since the token travels in a header.
- **2026-10-04 — Reload progress is polled (`GET /api/admin/gtfs-load-status`) while `POST /reload-gtfs` keeps blocking (F10).** Leaves the existing endpoint and `scripts/api.sh reload-gtfs` unchanged, and a 1 s poll is plenty for a load that takes minutes; SSE or an async job API would add more code for no visible gain. Progress is counted in zip bytes, not feeds, because feed sizes differ by orders of magnitude (Germany vs. Luxembourg).
- **2026-10-04 — Popups get an even whole-pixel size from JS (`snapToWholePixels` in `map.js`).** MapLibre positions a popup with `translate(-50%, -100%)`, so a text-dependent size like 254.8 × 296.75 px puts it between pixels and Chrome renders its text visibly soft. The size can only be measured after rendering, so it is set inline: an exception to "no inline styles". Only fully sharp at 100 % and 200 % display scaling; at 125 %/150 % MapLibre's whole-CSS-pixel anchor position can still fall between device pixels.
- **2026-10-06 — A popup that does not fit on screen pans the map instead of choosing another anchor (F20).** MapLibre places a popup below its point when there is too little room above, and never moves the map, so a long journey near an edge was cut off. A popup taller than the room on either side of its point cannot fit by any anchor, so `panIntoView` in `map.js` pans by the overflow after the final size is set.
- **2026-10-04 — Station names stay in the local language; search also matches accent-free, German-spelling and translated city names.** Display names match signs and tickets, which is also how Trainline's station data, HAFAS (DB/ÖBB/SBB) and MOTIS do it, but people type "cologne" or "koln". Translations come from a hand-written list of ~45 cities (`station-aliases.txt`), not Wikidata/GeoNames: a few dozen cities cover what people actually type, with no data pipeline or licence to handle. City names are replaced only as whole words, so "wien" never matches "Wiener Neustadt".
- **2026-10-04 — Translated stop names from `translations.txt` live in a `TransitGraph` map, not on `Station` (F11).** Only search needs them; a `Station` field would also appear in the `/api/stations` responses. Both the current format and the pre-2019 `trans_id` format are read, since feeds still ship either. Translations equal to the station's own name are dropped so feeds that list every stop in every language don't bloat the cache.
- **2026-10-06 — Rare trains are dropped at load (fewer than 8 days per train), and a station shows a journey up to 30 min slower if the fastest runs on fewer than half its days (B26).** The search has no travel date, so a one-off or timetable-change variant that is a bit faster won (NJ 479 on 3 days over NJ 469 on 194). Days are counted per train (route + train number), not per trip, because feeds split one train into many trips with few days each; trips without a train number are never dropped. The cutoff of 8 keeps seasonal and weekly trains, and every current feed spans at least 30 days. Past days are not ignored yet, because several feeds have expired (B24) and would disappear entirely. The preference only changes the journey shown per station, not which feeder a transfer uses, to keep the search's pruning unchanged.
