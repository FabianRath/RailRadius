How a reachability search runs

Three views of the same system: the round-based search, what the browser downloads and sends, and the flat arrays the server searches on. Every example uses the same small Austrian network, so you can follow one train from the map into the arrays.

1 · The search 2 · What the browser gets 3 · Data on the server

The question

From one start station, with at most N transfers, which stations can you reach, and how fast? There is no travel date and no start time: every train leaving the start can begin a journey, and a journey's duration counts from that train's departure. The search runs one round per transfer count, like RAPTOR.

Rounds on a toy network

Start: Wien, minimum transfer time 5 min (the example's window). Step through the rounds. Each round boards trains from the stations the previous round reached.

Durations count from the first train's departure at Wien. Passau is never reached: the only train there leaves Linz 3 min after the arrival, under the 5 min minimum.

Inside one round

Round 0 rides every trip from the start. Each later round runs these steps on the previous round's arrivals.

STEP 1

Group arrivals by station

The previous round's arrivals, minus those overtaken on all their days, grouped by station index and sorted by arrival time.

Stations then choose what to board in parallel on the fork-join pool: choosing only reads earlier rounds. The result is the same as on one thread.

STEP 2

Sweep departures against arrivals

TransferWindowInts: a sliding window over the station's sorted arrivals.

Each departure boards from the arrival inside the wait window (min … max) that gives the shortest journey so far. A later arrival can win if its journey started later. Slower arrivals board too, but only for days of the departing train that no faster one covers. Waits past midnight use a second window with the arrivals moved a day back.

STEP 3

Check the days

A transfer needs a day on which the whole journey so far runs and the next train runs.

Days are a WeekPeriodDays: one long, 7 weekdays × 9 six-week periods from this week's Monday (about a year, 63 bits). The check is one bitwise AND. Exact dates made the full-data search about 4× slower.

STEP 4

Ride boarded trips forward

Every stop after boarding becomes an arrival, unless pruning stops the ride.

TripProgressFlat keeps, per stop of each reached trip, the shortest duration and the days of rides recorded there. A ride stops as soon as it is no faster and all its days are already reached: an earlier ride got there with no more transfers and stays ahead for the rest of the trip.

Arrival time is part of the state, so a slower but earlier arrival that catches a better train is kept (B2), and so is a slower ride on days the faster one does not run (B33). Riding runs in station index order, after the parallel choice.

STEP 5

Choose each station's shown path

RegularJourneyChooser, once the round ends. Later rounds only add paths with more transfers, so this choice is final.

Candidates: the fastest ride with this transfer count and every ride at most 30 min slower. The shown path is the fastest that runs on at least half as many days as the most frequent candidate, so a slightly faster train that runs on a few days doesn't hide the regular one (B26).

A chosen path not faster than one with fewer transfers is left out. That is why Salzburg via Linz (2 h 55, 1 transfer) never shows in the toy: the direct IC takes 2 h 30.

Two ways to search, one result

The page runs the search in the browser when it can: the same Java search, compiled to WebAssembly with TeaVM, on a trimmed copy of the timetable. The server's SSE stream is the fallback. Both show the same stations, because both pick them through ShownStations.

preferred

In the browser

  • Used when the engine is ready, or becomes ready within 5 s of its load's start.
  • Runs in a Web Worker on one thread, so the page stays responsive.
  • Costs the server nothing per search, except a journey when a station is opened.
fallback

On the server (SSE)

  • When the engine isn't ready or fails. The stream then retries loading the engine.
  • Goes through admission, the rate limit and the gate.
  • Sends each round's stations as soon as the round ends.

Left out

  • Trip IDs, route names, train numbers, translated names: journeys are built on the server.
  • Station name index: station search stays on the server.
  • Departure index and regular departures: derived again when the file is read.

Why time differences

Within a trip, the gaps between times are small numbers that repeat across trains, and gzip compresses repeats well. Absolute times barely repeat.

Times as differences, on IC 540

The first stop has no arrival and the last no departure (NO_TIME). Reading undoes the differences per trip, back to seconds since midnight.

How the file got to 7.8 MB

gzip -9 sizes of each step, measured on the full data (docs/HOSTING.md). Brotli would save 2.7 MB more but needs a library. The engine itself, search.wasm, is 0.30 MB gzipped.

One graph, flat arrays

What the server serves is a ServedGraph: stations, trip infos, translated names, the station search index and the TimetableStore, swapped whole in one volatile field so a reader never sees a mix of old and new. How the arrays answer the search's questions

"Which trains leave station s?"

depStart[s] … depStart[s+1] is a slice of depSec and depEvent, already sorted by time (equal times in event order). The transfer sweep walks it in one pass.

"Ride trip t on from event e"

Events of a trip are contiguous: e+1 … tripFirstEvent[t+1]-1. Each gives evStation and evArrSec. evTrip maps any departure's event back to its trip.

"Does it run on those days?"

tripDayPattern[t] points into DayPatterns: each distinct calendar once, as exact ServiceDays (a bitset over epoch days) and as its WeekPeriodDays long, worked out once per day.

"Is this departure regular?"

regularDeparture is a bitset over departures. A ride ends where its trip leaves at a time that, over all trips leaving there then, runs on fewer than 8 days.

A search's scratch space

Per running search, a SearchScratch of flat arrays that are reused and never shrink (one per gate permit). Durations are chars (PackedMinutes, up to 65,534 min), because these columns hold millions of entries. Byte layouts per entry:

int (4 B)short (2 B)char (2 B)long (8 B)

Largest measured search, Stockholm with 5 transfers: ~171 MB scratch, ~195 MiB held while it runs. Labels 1.23 M used of 1.79 M, rides 1.24 M of 1.51 M, trip progress 2.98 M of 3.78 M slots.

A result in the cache

CompactResult holds, per station, its paths' transfers and minutes, plus only the labels of the chosen paths and the rides before them. No strings, no journey objects: a journey is built from the store when a station is opened. A stored 5-transfer result is ~1.3–1.8 MB, and the cache keeps at most 30.
