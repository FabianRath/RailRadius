# RailRadius — Architecture

_Read this only when you need detail beyond CLAUDE.md. Last reviewed: 2026-10-03._
_Describes the code as it is now. Update it in the same commit as any change it covers (see CLAUDE.md → Workflow). After a full check against the code, bump the date._

## Purpose

RailRadius answers the question **"Where can I get by train from station X with at most N transfers?"** across Europe.

It loads GTFS timetable feeds for ~25 European countries, keeps only **rail** routes, merges them into one network (with cross-border station deduplication) and lays its trips out as flat arrays (`TimetableStore`). It then runs a transfer-bounded, round-based search from a start station. The result is every reachable station with transfer count, total duration, path, and a leg-by-leg itinerary (train legs and transfer waits). The browser frontend (`frontend/`, served by the backend at `http://localhost:8080/`) draws the results on a MapLibre map with OpenFreeMap's dark style and receives stations live via Server-Sent Events.

## Tech stack

- Java 25 (JDK 25 required to build), Spring Boot 4.0.10 (`spring-boot-starter-webmvc`, actuator). Virtual threads are on (`spring.threads.virtual.enabled`): SSE streams run on Spring's task executor (`applicationTaskExecutor`, named explicitly because `@EnableScheduling` adds a task scheduler of the same type).
- Lombok (`@Data`, `@Builder`, `@Slf4j`, `@RequiredArgsConstructor`)
- Caffeine for the in-memory search result cache (`ReachabilityCache`)
- GTFS CSV parsing is hand-written (no GTFS library).
- Jackson 3 (`tools.jackson`, from Spring Boot) for the country borders GeoJSON; the data cache is a hand-written binary file (`BinaryBlocks`)
- Maven (wrapper `mvnw` / `mvnw.cmd`). Tests use JUnit 5 + AssertJ.
- Frontend tests: Node's built-in runner on the DOM-free modules, `node --test "frontend/test/*.test.js"` from the repo root (no `package.json`, no dependency).
- GitHub Actions: `.github/workflows/tests.yml` runs the backend tests, the browser engine check and the frontend tests (Java 25, Node 22) on each pull request into `main` or `perf` and each push to them; `dependency-submission.yml` sends the backend's Maven tree to the dependency graph when `backend/pom.xml` changes.
- Browser engine (#7): `browser-engine/`, a second Maven module, compiles the backend's search with TeaVM 0.17 to WebAssembly (Wasm GC, decisions.md #8) into `frontend/engine/` (gitignored; `search.wasm` and TeaVM's loader `wasm-gc-module-runtime.js`, unpacked from `teavm-core`), where the page loads it (#12); without that build the page searches on the server. An existing checkout needs `mvn -f browser-engine/pom.xml clean verify` once, since the loader's unpack marker sits in `target/`. It copies `backend/target/classes` and compiles its own stand-ins for the classes a browser can't run: `Parallel` (sequential: one thread), `BinaryBlocks` (only the reader, from the downloaded bytes), `SearchRefusal` (no Spring parent), plus an slf4j stub (WARN and ERROR to the console) and the `StringJoiner` and `ConcurrentLinkedQueue` that TeaVM's class library lacks. `BrowserEngine` is its entry: `load(file, today)` serves an unzipped `BrowserDataFile`; `search(start, maxTransfers, minWait, maxWait, maxJourneyMinutes, onRound)` searches like the stream, handing each round's newly shown stations to `onRound` as JSON in `ReachableStationSummary`'s shape (`ShownStations`, `BrowserJson`) and answering the total; `rides(station)` gives the rides of the path the last search showed there as `ride-journey`'s `rides`; `snapshot(sameResult)` is the oracle below, rides in store positions (strict) or as stations and times (same result).

## Running

Run from `backend/`; the cache paths are relative to the working directory. The commands below are for Git Bash; in PowerShell use `.\mvnw.cmd` instead of `./mvnw`.

- **Full data:** `./mvnw package -DskipTests && java -Xmx3g -XX:+UseCompactObjectHeaders -jar target/railradius-backend-0.0.1-SNAPSHOT.jar`
  - The app starts from the binary cache `data/gtfs-store.bin` (159 MB, S20): ~3 s in all, ~0.15 s of it reading the file. Without it, `--railradius.gtfs.auto-load-from-files=true` parses the zips (minutes) and writes it; so does `reload-gtfs`.
  - Server size, memory measurements and the launch checklist (proxy, systemd, firewall): `docs/HOSTING.md`.
- **Dev data:** `./mvnw spring-boot:run -Dspring-boot.run.profiles=dev -Dspring-boot.run.jvmArguments=-XX:+UseCompactObjectHeaders`
  - Austria + Hungary + Slovakia from `data/gtfs-dev/`, binary cache in `data/gtfs-dev-store.bin`.
- **Offline data (#21):** `scripts/mini-data.sh` (from the repo root) zips 12 `gtfs-mini` test feeds into `data/gtfs-mini/`, then `./mvnw spring-boot:run -Dspring-boot.run.profiles=mini` runs on them (44 made-up stations, cache `data/gtfs-mini-store.bin`). For places without the dev feeds, such as a Claude Code cloud session, whose proxy blocks the feed hosts. The script leaves out `alpha-fast-train` (a second `alpha`), `kappa`/`lambda` (their countries exist only in the test borders) and `eta`/`zeta` (their trains run in early 2026 only), and uses the JDK's `jar`, since Git Bash has no `zip`.
- **Claude Code cloud session (#21):** a Linux container with OpenJDK 21, so its environment's setup script installs JDK 25 and points `JAVA_HOME` at it. Its network allows `tiles.openfreemap.org` (map style, tiles, fonts), not the feed hosts. The `/run-dev` skill picks the `dev` profile when `data/gtfs-dev/` has zips, else `mini`.
- **Fresh checkout:** `backend/data/` is not in git, so there are no zips. Start the app (it starts empty), open the admin panel → Feeds, click "Download outdated" (it includes the `MISSING` feeds), then Tools → reload. Or with `scripts/api.sh`: `feeds-download-outdated`, then `reload-gtfs`. Which feeds are expected comes from `feeds.sources` (dev: austria, hungary, slovakia; default: every feed in `gtfs-feeds.txt`). `hungary` downloads only with MÁV credentials in `feeds.auth.hungary` (see Configuration).

- **Rollback:** the git tag `pre-compact` is the last version with the legacy engine and the JSON cache (`data/gtfs-cache.json`, `data/gtfs-dev-cache.json`, kept on disk for it). Its jar runs from those JSON files.

- **Search oracle (S12):** `SearchSnapshot` dumps every path a search returns, one sorted line each: station, transfers, minutes, the path's stations, each ride, the exact running days as epoch-day ranges and their label. One section per start and transfer limit 0–5, with today pinned, because it decides the days (B31). Two runs must give the same bytes. Two modes (#32, `GLOSSARY.md`):
  - **strict** names each ride's train: `tripId from departureSeconds to arrivalSeconds` (`RideFormat.TRIP_IDS`), or store positions in the browser check. A change that only makes the search faster must pass it: it proves not even the train chosen changed.
  - **same result** names each ride only as `boardStation departureSeconds alightStation arrivalSeconds` (`RideFormat.STATIONS_AND_TIMES`, from the store, so the browser engine writes it too). A change that moves trips or events around in the data must pass it: of two trains with the same stops and times on a ride, either may be named, but any change of a station, time or running day shows.
  - gtfs-mini: `SearchSnapshotTest` compares a search from every station of each feed combination with the recordings, strict in `src/test/resources/search-snapshots/` and same result in its `same-result/`. It holds both the graph as loaded and the graph read back from the binary store file to them. After an intended change, rewrite them with `./mvnw -q test -Dtest=SearchSnapshotTest -Dsnapshot.update=true` and explain every changed line.
  - Browser engine (#10): `BrowserDataFileTest` searches from every station on the browser file in the JVM and must find what the full store finds, with each ride as store positions (`RideFormat.STORE_POSITIONS`: trip, board event, alight event; the browser file has no trip IDs), and what the same-result recording holds. It leaves each combination's file, the server's strict dump and the same-result recording (`<combination>.same-result.txt`) in `backend/target/browser-engine-check/`. `mvn -q -f browser-engine/pom.xml verify` (after the backend's `test`, with Node on the PATH) builds the engine and runs `src/test/js/check.mjs` from `BrowserEngineCheckTest`: it searches each file in WebAssembly and fails on the first line that differs from the server's strict dump or the same-result recording; then it runs every snapshot search through `search` and `rides`, with no journey limit and with 60 min, and checks they show what the stream shows: each station once, with the transfers, minutes and rides of its first path within the limit.
  - Dev and full data: the starts of one set in `docs/bench-stations.txt`, searched on a binary cache file and written to the gitignored `data/snapshots/` (gzipped if the name ends in `.gz`; a full-data dump is several GB as text), in the mode given last (`strict` or `same-result`): `./mvnw spring-boot:run -Dspring-boot.run.main-class=com.railradius.service.SearchSnapshot "-Dspring-boot.run.jvmArguments=-Xmx3g -XX:+UseCompactObjectHeaders" "-Dspring-boot.run.arguments=data/gtfs-dev-store.bin dev 2026-10-09 data/snapshots/dev-2026-10-09.txt.gz strict"`. For full data use `data/gtfs-store.bin full` (2.7 M lines, 136 MB gzipped). Compare two dumps with `cmp`, and list the differing lines with `diff <(gzip -dc a.txt.gz) <(gzip -dc b.txt.gz)`.

**Startup flow:**
1. `GtfsDataService` loads the binary cache file (`BinaryCacheStore`) if present and of the current format version. Otherwise it parses the zips only if `auto-load-from-files` is true (true for dev, false for default) and the GTFS directory has a zip; with none (fresh checkout) it logs a WARN and starts empty. With no data, use `POST /api/admin/reload-gtfs`.

## Source files

Package `com.railradius.<sub>` lives in `backend/src/main/java/com/railradius/<sub>/`.

| File | Package | Role |
|---|---|---|
| `RailRadiusBackendApplication` | root | Spring Boot entry point, `@EnableScheduling` and `@EnableAsync` |
| `RailRadiusController` | controller | Public API under `/api` |
| `AdminController` | controller | Admin/debug API under `/api/admin` |
| `GtfsDataService` | service | Fills the `TransitGraph` at startup (binary cache file, else the zips) and on `reload-gtfs`: loads the zips into a `RailNetwork`, merges its stations, builds what is served (`RailNetwork.servedData`), writes the binary cache file, then serves it (`TransitGraph.serve`) and clears the reachability caches, then has `BrowserDataStore` build the browser file; startup from the binary cache goes through the same step. One load from the zips at a time: one asked for while another runs throws `GtfsLoadRunning` and builds nothing (#20). `/admin/gtfs-stats` reports `dataLoaded` from `TransitGraph.isDataLoaded`, as `/health` does. While a load runs, its progress counts come from the network being built |
| `TransitGraph` | service | Holds the served graph (`ServedGraph`) in one `volatile` field and answers from it: stations, their translated names, the `TripInfo` of each store trip, each feed's `FeedTimespan` (`feedTimespans`, read by `FeedAlerts`) and the `TimetableStore` (an empty one before a load); `nextStationCount` (a station's edges, from the store), `stoppingTripCount` (the store trips that stop at a station), `upcomingDays` and `todayEpochDay` (by its `Clock`). `serve` replaces the served graph whole with what the binary cache, a load or a browser file gives, so a reader sees the graph from before or the new one, never a mix (#18); a reader that needs several values from one graph takes `served()` once. Everything that reads GTFS data injects this |
| `ServedGraph` | service | The served graph (see `GLOSSARY.md`): an immutable record of the stations, translated names, trip infos (`TripInfos`, `tripInfo(trip)` by store trip index), `TimetableStore`, feed timespans and the station search index. `ServedGraph.of` builds it, index included, from `BinaryCacheData`, or from a `BrowserDataFile`'s `BrowserData` without translated names, trip infos, feeds or index (the browser's graph) |
| `RailNetwork` | service | The merged network while the zips are loaded (S21): stations, translated names, edges (`neighbors`), every edge's connections, trips' stop lists, `TripInfo`s and `ServiceDays`, stop → trips, and each feed's `FeedTimespan`. The station merging reads and remaps it; `servedData` then builds the `TimetableStore` from it, and it is dropped |
| `GtfsFeedLoader` | service | Parses the rail part of each zip into the `RailNetwork`, with per-feed stop dedup; returns the zips it read |
| `RailTripReader` | service | A feed's rail routes (name, operator from `agency.txt`) and rail trips (route, service ID, `TripInfo`) from routes/agency/trips.txt |
| `RareTrainFilter` | service | Drops a feed's trains that run on fewer than 8 days, all their trips together, before the graph is built (B26). A train is route + train number (if any, B32) + first stop + departure time (B33). `regularDepartures`: per stop of a trip, whether all trips leaving there at that time run on 8 days or more; the search doesn't ride a trip away from a stop where they don't (B33) |
| `ServiceCalendarReader` | service | A feed's services and the days they run, from `calendar.txt` (weekly pattern in a date range) and `calendar_dates.txt` (days added or removed) |
| `ServiceDays` | service | The days one service runs, as a bitset over epoch days; `from(epochDay)` for the days from today on, `intersect(later, dayShift)` and `union` for a journey's shown days and the rare-train rule, `dayCount`. `EVERY_DAY` for trips without a calendar entry |
| `WeekPeriodDays` | service | The search's coarse days: a `long` with one bit per weekday of each of 9 six-week periods from the Monday of today's week (about a year), set if the service runs on such a date from today on; `movedForward` for a wait past midnight. `OfDay` caches the masks per service for one day (`TransitGraph.weekPeriodDays`) |
| `TripInfo` | service | A trip's train number (`trip_short_name`, leading zeros of a numeric one stripped, prefixed with a `TrainCategories` category), headsign and operator |
| `TripInfos` | service | The `TripInfo` of each store trip as three string columns by trip index (#35), not a map keyed by trip ID; read from the store file, equal strings share one instance. Empty on a browser's graph |
| `TrainCategories` | service | Where a train's category comes from: per source the trips.txt column that holds it, from `train-category-columns.txt` (Netherlands `trip_long_name`, Poland `plk_category_code`); else, for bare train numbers, rules by source, agency, route type and optionally route short name, from `train-categories.txt` (e.g. DELFI's DB Fernverkehr: 101 → `ICE`, 102 → `IC`/`ECE`) |
| `GtfsLoadRunning` | service | A `ResponseStatusException` with 409 Conflict: a load from the zips was asked for while another runs (#20) |
| `GtfsLoadProgress` | service | Phase (PARSING → MERGING → SAVING → DONE/FAILED), feeds and zip bytes parsed of the running or last load from the zips; read by `/gtfs-load-status` |
| `TripRowBatcher` | service | Buffers stop_times rows per trip and hands whole trips to the loader in batches |
| `StopNameTranslations` | service | A feed's translated `stop_name`s from `translations.txt`, by stop ID or by untranslated name; reads the current and the pre-2019 (`trans_id`) format |
| `GtfsCsvReader` | service | Row-by-row reader for one CSV file inside a GTFS zip, at the top level or inside one top-level folder (ÖBB); strips a UTF-8 BOM from the header |
| `StationSearchIndex` | service | Station name search over the name variants of each station's name and translated names: trigram → station positions, in degree order. The index (`StationSearchIndex.Index`) is part of the `ServedGraph`, built by `StationSearchIndex.build` with it; `search` reads the one served now |
| `StationNameVariants` | service | Searchable forms of a station name: folded (lowercase, no accents), German umlaut spelling (`koeln`), and the local city name replaced by its translations from `station-aliases.txt` (`cologne`) |
| `StationCodes` | service | Cross-border rule: the UIC station code in a stop ID, by per-source formats from `station-codes.txt` (`france:StopArea:OCE87146217` and `switzerland:8714621` → `8714621`) |
| `StationNameMatcher` | service | Cross-border rule: name similarity and name containment of two nearby stations (see Data pipeline → cross-border dedup) |
| `StationDeduplicator` | service | Within-country and cross-border station merging after all feeds are loaded; runs the merge rules in order |
| `StationGrid` | service | Stations bucketed into square degree cells; `near` = the 3×3 cells around a station |
| `SharedTrainMatcher` | service | Cross-border rule: two stops are one station if ≥ 3 trains serve both at the same minute with the same neighbour station |
| `HomeCountries` | service | A feed's home country: where more than half of its located stations lie; used by `ForeignStopSnapper` and `CoverageService` |
| `CoverageService` | service | Covered countries for `/api/coverage`: the distinct home countries of the loaded feeds, so a cross-border train's last stops abroad don't add a country |
| `ForeignStopSnapper` | service | Cross-border rule: a feed's stop outside its home country is merged into the nearest station of that country's feed (≤ 1 km), or one of the same name (≤ 5 km) |
| `FeedUpdateCenter` | service | Update center for the GTFS zips: status of each zip (`FeedStatus`, its `FeedTimespan` memoized per file and modification time; a big feed takes seconds, as trips.txt is read too) plus a `MISSING` status for each expected feed (`railradius.feeds.sources`) without a zip, a scheduled log check (`railradius.feeds.check-interval`, first run at startup) that WARNs about missing, expired and expiring feeds, disk space of the zips in use and in `previous/` (`FeedStorage`), and downloads of registered feeds. A download is refused (`BUSY`) during a GTFS load or another download |
| `FeedValidity` | service | First and last day any service of a feed runs, from `ServiceCalendarReader` over the whole feed (not only rail) |
| `FeedTimespan` | service | How long a feed's trains run: its `FeedValidity` and `EarlyEndingOperators`; `trainsEnd` is the last day, or the earlier last day of the first early-ending operator. Read per zip by `FeedUpdateCenter` and on each load by `GtfsFeedLoader` (from the whole calendar, before the rare-train filter), and stored in the binary cache, so a server without zips has it too. None for a feed without a calendar |
| `FeedAlerts` | service | Feed alert mail (F29): at `feeds.alerts.cron` (daily 08:00), if turned on, one mail to `feeds.alerts.to` listing every served feed (`TransitGraph.feedTimespans`) whose trains end within `feeds.alerts.days` (14) or already have, minus paused ones; nothing when none is due. On/off and the pauses (source → the `trainsEnd` it was paused at) are kept in `feeds.alerts.settings-file` (JSON), so they survive restarts; a pause only applies while the feed's `trainsEnd` is still that day, so new data for it ends the pause. ## Data pipeline (`GtfsDataService.loadFromFiles`)

Everything below fills a load-time `RailNetwork`, which is dropped once the served data is built from it (step 8). `GtfsFeedLoader`, for each `data/gtfs/*.zip` (sorted). The source name comes from the filename, e.g. `gtfs_germany.zip` → `germany`:
1. **routes.txt / agency.txt** (`RailTripReader`): keep only rail route types `2`, `100–106` and `109` (S-Bahn), each with its operator (`agency_name`; a route without `agency_id` gets the feed's only agency).
2. **stops.txt / trips.txt / calendar**: load stops and the rail trips: route, service ID and `TripInfo` (train number, headsign, operator). `ServiceCalendarReader` reads the days of each service; the services of rail trips go to the network as `<source>:<serviceId>`. A trip whose service is in neither calendar file (or whose feed has neither) runs every day, with a WARN count. `RareTrainFilter` then drops every train that runs on fewer than 8 days of the feed, past days included: one-off specials and timetable-change leftovers (B26: NJ 479 ran 3 days, the regular NJ 469 is 15 min slower from Aachen). A train is all trips of one route with the same train number that leave the same first stop (canonical, so platforms match) at the same time, because feeds split one train into several trips with different days. Trips without a train number (all of norway, france, hungary, …) are grouped the same way (B32), and the departure keeps a rare timing variant of a regular train apart from it (B33: ICE 104 from Köln at 19:17 on 6 days). For this the filter reads stop_times.txt once more beforehand, keeping only each trip's first row. A train with a trip that has no calendar entry is kept, and so is a trip without stop_times. A trip with a value in its feed's category column (`train-category-columns.txt`) gets that category in front of its train number: `2835` → `Intercity 2835`, `1900/1 Zosia` → `IC 1900/1 Zosia`. Otherwise a numeric train number on a route that matches a `train-categories.txt` rule gets the rule's category: `002310` → `ICE 2310`.
3. **Per-feed stop dedup**: a stop whose `parent_station` is in the feed (with coordinates) is merged into that parent, at any distance. The other stops are merged when they have the same name and lie within ~0.0015°. IDs are canonicalised to `<source>:<id>`, with `_ARR`/`_DEP`/`ARRIVAL_` style suffixes and prefixes stripped.
4. **stop_times.txt**: streamed and buffered per trip (`TripRowBatcher`), rail trips only, and handed to the network in batches of `railradius.gtfs.trip-batch-size` (100k) trips. A batch is only cut where a new trip starts, so trips stay whole in files grouped by `trip_id`. If a trip shows up again after another one started, the rest of the file is read in one batch, and rows of a trip already built are dropped with a WARN. Each trip's consecutive stop pairs produce:
   - `neighbors`: stopId → neighbour stopIds
   - `connections`: `"from->to"` → list of `Connection`
   - `tripStops`: tripId → ordered stop list; `tripInfos`: tripId → `TripInfo`; `tripServiceDays`: tripId → its service's shared `ServiceDays`; `stopTrips`: stopId → tripIds

   Then `translations.txt` (optional, `StopNameTranslations`): each stop's translated `stop_name`s go to its canonical station in `translatedNames` (stopId → names), minus the station's own name, for stations that a rail trip added. Only search uses them; the API returns the original name.

A feed that adds no connections at all (e.g. unreadable headers) is logged as a WARN.

After all feeds are loaded (`StationDeduplicator`, then `RailNetwork.mergeStations`), every station first gets its `country` from `CountryLocator`; a merge keeps the canonical station's country.
5. **Within-country dedup**: same exact name, same source, within ~200 m.
   **By station code** (`StationCodes`, B30): stations of different sources with the same UIC code (from the stop ID, formats in `station-codes.txt`) merge when at most 5 km apart (`SAME_CODE_MAX_DISTANCE_METERS`), the better connected one canonical. Catches stations where one feed's coordinates are 1–4 km off (the Swiss feed's French stations, Trenord vs Trenitalia, Austria vs Italy). The limit keeps codes that repeat far away apart (the Austrian numbers repeat per state).
6. **Cross-border dedup**, on pairs of stations of different sources within ~500 m (found via a ~1 km `StationGrid`), in two passes:
   - **by name** (`StationNameMatcher`): word-set Jaccard similarity ≥ 0.4; or, within ~100 m, every word of one name is in the other ("Split" / "Split željeznički kolodvor"). Words are compared folded (`StationNameVariants.fold`), Cyrillic transliterated (Bulgarian system), without words for "station" and link words (stazione, kolodvor, di, …), with "C.LE" → centrale, "Hbf"/"…bf" → (haupt)bahnhof, airport words as one, and oe/ae/ue as o/a/u ("Koebenhavn"); two words also match one edit apart from 5 letters on and two edits apart from 8, if they start with the same letter. The best score over the names' city translations (`StationNameVariants.variants`: Padua / Padova) counts. The ~100 m limit keeps nearby separate stations apart (Cotral's "Viterbo" / "Viterbo Porta Fiorentina", 126 m);
   - **by shared trains** (`SharedTrainMatcher`): at least 3 trains leave both at the same clock minute towards the same next station (or arrive from the same previous one), neighbours compared after the merges so far. Catches translated names ("Aachen, West Bf" / "Aix-la-Chapelle Ouest"). Repeated until a pass merges nothing.

   In both, the station with more connections becomes canonical.
7. **Foreign stops** (`ForeignStopSnapper`): a source's home country is where more than half of its located stations lie. A stop outside its source's home country is merged into the nearest station within 1 km of a source at home in the stop's country, which stays canonical. With none that close, it is merged into the nearest one within 5 km whose name has the same words, ignoring a country in brackets at the end (`StationNameMatcher.sameName`: "Apach(fr)" / "Apach"; B30), as some feeds place their stops abroad 1–4 km off. Every map is remapped. A canonical station can itself be merged later (A→B, then B→C); `mergeStations` first resolves such chains so every alias maps straight to the last station. The alias's translated names move to the canonical station.
8. `RailNetwork.servedData` builds the `TimetableStore` from the network's trips (`MergedTrips`, `TimetableStoreBuilder`, then the rare-departure check per station and departure time) and takes the `TripInfo` of each store trip and the `FeedTimespan` of each feed. `BinaryCacheStore` writes that to the binary cache file (format version 3), and `TransitGraph.serve` makes it what the app serves, exactly as a start from the binary cache does (S21). Then `BrowserDataStore` builds the browser file of the new graph in the background (#9). Every stop ID in the network is the station's own String instance, not a copy per trip (S16).

`StationSearchIndex.build` indexes the variants of each station's name and translated names, by degree (`nextStationCount`).

## Reachability algorithm (`SearchAdmission`, `ReachabilityCache`, `CompactReachabilitySearch`)

**One engine (S21).** `CompactReachabilitySearch` searches the `TimetableStore` by the rules below and the Search semantics contract; journeys, legs and running days are built from the store too (S19). The legacy engine (`ReachabilitySearch` on `SearchTimetables`) gave byte-identical oracle dumps and was deleted in S21; the tag `pre-compact` has it. A round's rides are rows in `RoundRides` (a ride per boarded trip, its arrivals worked out again from it when the next round groups them), and only the arrivals that become candidates or are boarded from get a label in a `LabelArena`. Per-trip and per-station state are flat arrays reused from search to search (one `SearchScratch` per search running at once, so up to `search.gate.permits` of them stay allocated), and after each round's boardings are chosen the arena keeps only the labels later rounds reach (the rides before the arrivals boarded from, and the chosen paths). Exact days for the chooser are worked out once per label, by ascending transfers. The largest searches use a ~170 MB scratch and hold ~195 MiB while they run (S23, `docs/HOSTING.md`).

`SearchAdmission.admit` is the central dispatcher, over the results stored in `ReachabilityCache`. It is keyed by `SearchOptions(start, maxTransfers, minTransfer, maxTransfer)`:
1. **Raw cache hit** → return the stored result immediately.
2. **Cut down**: if a result with more transfers (same start and window) is stored, keep only its paths with ≤ N transfers. A round never depends on later rounds, so this equals a search with N.
3. **Search** (`CompactReachabilitySearch.search`), stored afterwards. Every key is a `SearchOptions`, which can't hold an out-of-range value, and on the request path comes from `SearchRequestValidator`, so an unknown station or an out-of-range parameter never reaches the cache, the rate limit or the search. Before searching, `SearchAdmission` charges a visitor's search to its client key's `SearchRateLimiter` budget (IPv4 address or IPv6 /64) (stored results and admins are free; the charge is decided by the same lookup that serves a stored result, so a result evicted meanwhile is never searched for free, #16); over budget, nothing is searched. It runs inside a `SearchGate` permit, so every search (stream, `/journey` after an eviction, warmer) counts against the same limit. A search beyond `search.gate.permits` (2) waits in a fair queue and checks the stored results again once it has a permit, since an equal search may have finished meanwhile. When `search.gate.max-queued` (6) searches already wait, it is refused with `SearchRefusal` `BUSY` (HTTP 503; an SSE `error` event on the stream). A search that runs longer than `search.deadline-ms` (30 s, counted from when it got its permit) stops before its next round or its next station's boardings, logs a WARN with its parameters, stores nothing and frees its permit (`SearchRefusal` `TOO_SLOW`: HTTP 503; an SSE `error` event on the stream; the warmer logs it and moves on). It is a backstop for parameters the rate limit prices too low (S33). **An equal search running now** (same `SearchOptions`, S37): a caller that finds one in `InFlightSearches` waits for its result instead of searching, before the gate, so it holds no permit and no queue place; meanwhile its listener's `queued` tick runs about every second, so a waiting stream whose client is gone stops (its own failed send) without touching the running search. The waiter gets the result like a stored one, or the running search's failure (deadline, busy, out of memory, …); only if that search stopped because its own client is gone (`CancellationException`) does the waiter search itself, possibly becoming the one others wait for. Only identical keys wait: a lower transfer count does not wait for a running higher one. A waiter is still charged by the rate limit like any unstored search (see `decisions.md`). A full-data 5-transfer search holds about 200 MB while it runs and each permit keeps its scratch, so the permits bound the heap a burst of visitors can take: at 2 permits the full data runs at `-Xmx1280m` (S25, `docs/HOSTING.md`).

The search has no start time: every trip leaving the start station can begin a journey, and duration counts from its departure. It runs one round per transfer count (like RAPTOR):
- Round 0 rides every trip from the start station. Round k boards trips from the arrivals of round k−1. Riding a trip forward records each stop as an arrival.
- **Pruning is per trip**: each trip keeps per stop the shortest duration, the days (`WeekPeriodDays`) of that ride and the days of every ride recorded there (`TripProgressFlat`). A ride stops as soon as it cannot beat the duration and all its days are already reached, because earlier rides got there at the same time with no more transfers and stay ahead for the rest of the trip. On some of those days the shown journey can be a bit slower than the fastest possible. Arrival time is part of the state, so a slower but earlier arrival that catches a better train is kept (B2), and so is a slower ride on days the faster one doesn't run (B33).
- **Transfers**: per station and round, departures are swept in time order against the arrivals sorted by time (`TransferWindowInts`). Each departure is boarded from the arrival that catches it within the min/max wait window with the shortest journey so far, then from slower ones only for days of the departing trip that no faster one covers. Waits past midnight use a second window with the arrivals moved a day back. Stations choose what to board in parallel on the common fork-join pool, since that only reads earlier rounds; riding the boarded trips writes the per-trip state, so it runs afterwards in station index order (arrivals are grouped by station index, each station's in the order they came), and the result is the same as on one thread. Choosing each station's path at the end of a round is parallel too; the exact days are worked out once per label (`LabelDays`), each transfer count's labels in parallel.
- **Service days (B25, B31, B33)**: there is no travel date, but a journey's days start with its first train's days from today on, so a train whose days are all past, like every train of an expired feed, is never boarded. A transfer needs a day on which the whole journey so far runs and the departing train runs too (for a wait past midnight: the day after). Days are compared as `WeekPeriodDays` (weekday × 6-week period), not dates: exact dates made the full-data search about 4× slower (see decisions.md). So trains running on the same weekdays of the same period but in different weeks can connect; the shown journey then has no common date and the station details say so (`hasCommonDay`). Each ride carries its journey's days, counted on its own trip's service day. Checking only consecutive trains let a chain of six trains pass whose first three ran only in autumn and last two only in spring, bridged by an all-year regional train. If the window's best arrival fails the check, the arrivals in the wait range are scanned for the best one that passes. Feeds whose validity periods don't overlap therefore don't connect at transfers. A ride also ends at a stop where its trip leaves at a time that, over all trips leaving there then, runs on fewer than 8 days (`RareTrainFilter.regularDepartures`): a variant that matches its regular train at the first stop is not ridden past the point where it deviates. Trips with the same stations and times (one train published as several trips with different days, or the same train in two feeds: 390k of 840k trips on the full data) are one search trip that runs on all their days; under the whole-journey check that is exact.
- **Result**: per station, a list of paths by ascending transfers. During the search, each station keeps per transfer count the fastest ride and every ride at most `MAX_SLOWER_MINUTES` (30) slower, all faster than every ride with fewer transfers. Rides are kept as `previous` pointers. When round k ends, every station it reached gets its path with k transfers: `RegularJourneyChooser` picks one among the candidates with k transfers (later rounds only add rides with more transfers, so these are final): the fastest that runs on at least half as many days as the most frequent candidate (`JourneyRunningDays.withRide`, worked out once per ride because candidates share their earlier rides; no calendar data counts as often enough). Only the chosen ride is kept as a path: its label, which the arena keeps from then on. Without a start time, every departure of the day with a similar duration is a candidate (tens per station on the dev data), so the check per arriving ride compares only against the fastest duration per transfer count (O(1)). So a slightly faster train that runs on few days doesn't hide the regular one (B26). A chosen path that is not faster than the one with fewer transfers is left out. Only the shown journey changes: a transfer still continues from the fastest arrival (the `TransferWindowInts` sweep), so a later train is only reached via the faster feeder.
- The response picks per station the path with the fewest transfers that fits `maxJourneyTimeHours` (B4). Without a limit, that is the first path.

Overnight wrap: a time difference below −60 min gets +24 h added.

**Timing log:** each search logs one INFO line (`Search stats`) with the stop arrivals, trips and stations, the time of the whole search and of choosing paths at the end of each round, the departures scanned and boarded, and how often `TransferWindowInts` had to scan the wait range because its best arrival failed the day check (with the arrivals those scans checked, and their time summed over the threads, estimated from one departure event in 64). The same per round is logged at DEBUG. A stream also logs its total time and when it sent the first stations.

`JourneyLegBuilder` merges consecutive connections into one TRAIN leg (same tripId, or same route name and continuous in time) and inserts TRANSFER legs between them. A TRAIN leg's train number, headsign and operator come from its first trip, looked up by its store trip index. Its `fromStopId`/`toStopId` are the boarding and alighting stops as they appear in `path`, which lists every stop the trains call at; while a station's details are open, the frontend (`js/journey.js`) uses them to draw one straight-segment line per train through those stops, coloured by the train's index like the transfer levels, and hides all stations not on the path.

`JourneyRunningDays` intersects the days of every ride on the path, counted from the first train's service day and from today on (B31): a ride boarded at an earlier clock time than the previous one arrived is shifted by a day (the search's overnight transfer). A ride's days are the union of its trip's and those of every trip leaving the boarding station and reaching the alighting station at the same times, because feeds publish one train as several trips with different days and the search keeps only one. The summary is the weekdays on which the journey runs on at least half of their dates ("Runs daily", "Runs Mon–Fri", "Runs Sat, Sun"); with fewer than 4 days or no such weekday it is "Irregular: N days in the timetable". No dates are shown. The search compares days by weekday and period only, so a journey can have no common date; `hasCommonDay` is then false and the station details show a warning instead of the summary.

The wait limit applies to each transfer, so a journey can bridge a longer wait by riding away and back to the same station (F24); it arrives no earlier than waiting would. `JourneyLegBuilder` sets `roundTripStation` to the name of the station in `path` that occurs more than once and is visited first (for a ride out and back on one line, the station where the loop starts, not a stop on the way), and the station details show a warning naming it. Such journeys are not filtered out.

**Caching layers:**
- `ReachabilityCache` (Caffeine, max `cache.raw-max-entries` (30) results) holds raw results (`CompactResult`: per station its paths' transfers and minutes, each path's journey built when asked for). A stored result also answers every lower transfer count. A result holds no strings or objects per path, only the labels of its chosen paths and the rides before them (the `Search stats (compact)` line logs its size).
- **Predictive warming**: after a streaming request with N < `predictive-max-transfers` (5), `ReachabilityWarmer` searches that maximum with the same transfer window on a background thread, into the raw cache. Every count from N+1 up is then cut down from it. It only searches if a gate permit is free, no search is queued and no equal search runs (`SearchAdmission.warmIfIdle`), otherwise it skips, so it never delays a visitor and never waits. A visitor's equal search started while it warms waits for it (S37).

**Streaming** (`calculateReachabilityStreaming`): a search sends each round's stations as soon as the round ends; a stored result is sent at once. A station is sent once, with its first path within `maxJourneyHours`; paths come by ascending transfers, so that is the path the response picks too (B4), and a later round never changes a sent station. Stations go out as `ReachableStationSummary`s (no path, legs or running days: on the full data those made the stream about 100 MB) in SSE `stations` events in batches of 30, followed by a `done` event (`{total, calculationTimeMs}`), or an `error` event on failure (also when the search is refused (`SearchRefusal`: the request is invalid, the client is over its rate-limit budget, the gate's queue is full, or the search ran past its deadline, S33), or it ran out of memory: B38). Those send their own message; any other exception is logged and sends a fixed generic text, never the exception's message (B43). While the search waits for a gate permit or for an equal search running for another client (S37), the stream sends an SSE comment (`:queued`, ignored by `EventSource`) about every second; a stream that waited for an equal search sends its result at once when that one ends, like a stored result. A failed send means the client is gone: the search stops at the next round's send (or while queued), stores nothing and frees its permit. A stream times out after 2.5 × `SearchAdmission.longestWait()` (`STREAM_TIMEOUT_FACTOR` in `RailRadiusController`, S36): the longest legitimate stream waits 3 deadlines in the queue and runs its own search, 2 min at the defaults, so 5 minutes; a timed-out stream's sends fail, so its search stops the same way.

## Search semantics contract

What the search must keep, so a rewrite gives the same result as `SearchSnapshotTest`'s goldens. One rule, one test (`ReachabilityServiceTest` unless named otherwise):
- **Slower arrival kept (B2):** a slower arrival at a station is kept when it catches a train the fastest arrival misses. `slowerEarlierArrivalIsKeptWhenItEnablesAFasterTransfer`
- **Past midnight (B25):** a transfer whose wait crosses midnight boards a train running the day after a day of the journey so far. `transferPastMidnightBoardsATrainRunningTheNextDay`
- **From today (B31):** a journey's days start with its first train's days from today on, so a train whose days are all past is never boarded. `trainsWhoseDaysAreAllPastAreNotRidden`
- **Whole journey (B33):** a transfer needs a `WeekPeriodDays` day on which every train of the journey so far runs together with the next one, and a faster ride does not cut off a slower one on days it lacks. `journeyWhoseTrainsShareNoDayGivesWayToOneThatRuns`
- **Regular journey (B26):** a station shows, among its candidates with the same transfer count (the fastest and those at most 30 min slower), the fastest that runs on at least half as many exact days as the most frequent one. A train over 30 min slower is no candidate, so a much faster rare train beats it. `rareTrainMoreThanHalfAnHourFasterStillWins`
- **Merged trips:** trips with the same stations and leg times are one search trip that runs on the union of their days and keeps the smallest trip ID. `TimetableStoreTest.tripsWithTheSameStationsAndTimesBecomeOneThatRunsOnAllTheirDays`
- **Twin trips:** a ride's exact days are its trip's days united with those of every trip leaving the boarding station at the same time and reaching the alighting station (at its first later visit) at the same time (`TimetableStore.rideDays`); the ridden trip always counts, also when it passes the alighting station twice (B37, `JourneyRunningDaysTest.aRideToALoopTripsSecondVisitRunsOnTheDaysOfEveryTripMergedIntoIt`). The test covers twins that are also merged; twins differing elsewhere on the trip have no test yet. `rideRunsOnTheDaysOfEveryTripWithTheSameTimes`
- **Rare departures:** a ride ends at a stop where its trip leaves at a time that, over all trips leaving there then, runs on fewer than 8 days. `rideEndsWhereItsTripLeavesAtATimeThatRunsOnFewDays`
- **Overnight window:** a wait past midnight lies within the min/max wait and is at most 24 h − 61 min (`GtfsTime.MAX_OVERNIGHT_GAP_SECONDS`), so a train leaving up to an hour before the arrival's clock time is not caught the next day. `trainLeavingLessThanAnHourBeforeTheArrivalIsNotCaughtTheNextDay` (the wrap itself: `transferAcrossMidnightWrapsToNextDay`)
- **Start excluded:** a ride through the start station records no arrival there, so no journey transfers at or ends at the start; its result is the one empty path. `CompactReachabilitySearchTest.startStationKeepsOnlyItsEmptyPathThoughATrainReturnsToIt`

**Processing order.** Ties are decided by who comes first, so the result depends on this order:
- **Numbering:** trips are walked in trip ID order (string order). Station indexes follow the first appearance of each stop on that walk. Merged trips get indexes in the order of their smallest trip ID.
- **Departures at a station:** by departure seconds, equal times in trip index order (a stable sort).
- **Round 0:** the start's departures in that order. Each trip is ridden stop by stop.
- **Round k:** the previous round's arrivals, minus those a faster ride of their own round overtook on all their days, grouped by station index ascending. Within a station they keep the order they arrived in, then are sorted stably by arrival seconds. Departures are matched in departure order. Each one boards first from the arrival with the shortest journey so far, then from slower ones for days no faster one covers. Overnight beats same-day only when it is strictly shorter. Boarded trips are then ridden station by station in that order.
- **Tie-breaks that depend on that order:**
  - `TripProgressFlat` keeps the first ride's duration and days when a later one is equally fast.
  - `TransferWindowInts`' queue prefers the later arrival when two give the same journey start. Its fallback scan prefers the earlier one.
  - `StationCandidatesFlat` keeps rides in the order they were offered. `RegularJourneyChooser` takes the first of equally fast candidates.

"Feeds" (`js/feeds.js`) widens the panel to nearly the whole window and lists every zip and missing feed from `/feeds`: last service day (first day as a tooltip), days left, state with the early-ending main operators below it, size, download date, source host, and a download button for feeds in `gtfs-feeds.txt` ("manual" otherwise). During a reload it shows a progress bar with phase, feeds, % parsed, elapsed time, ETA and graph size. "Alerts" (`js/feed-alerts.js`, also wide) shows `/feeds/alerts`: an "Email alerts: on/off" toggle, "Send test email", whether mail is configured and to whom, and the served feeds due within the alert days (trains end, days left, early-ending operators, last service day, paused or not) with a Pause/Resume button each.

## Configuration (`application.yml`, prefix `railradius.`)

- `gtfs.directory` (`./data/gtfs`, env `GTFS_DIRECTORY`), `gtfs.auto-load-from-files` (false: a start without the binary cache starts empty), `gtfs.store-file` (`data/gtfs-store.bin`; the binary cache, S20)
- `browser-data.directory` (`data/browser-data`): where `BrowserDataStore` writes the browser file
- `feeds.expiring-days` (30): feeds that end, or whose first early-ending main operator stops, within this many days are `EXPIRING`; `feeds.check-interval` (`PT24H`): how often the missing/expired/expiring feeds are logged; `feeds.sources` (empty = every feed in `gtfs-feeds.txt`): comma-separated feeds expected in the GTFS directory, listed as `MISSING` without a zip; `feeds.auth.<source>` (no default, never in git): credentials that `gtfs-feeds.txt` headers refer to, e.g. `feeds.auth.hungary` = base64 of `user:password` for MÁV's Basic auth. Set it in `backend/config/application.yml` (gitignored; Spring Boot reads `config/` in the working directory on top of the bundled file) or as env var `RAILRADIUS_FEEDS_AUTH_HUNGARY`
- `feeds.alerts.days` (14): served feeds whose trains end within this many days, or already have, are in the alert mail; `feeds.alerts.cron` (`0 0 8 * * *`): when it is sent; `feeds.alerts.settings-file` (`data/feed-alerts.json`, dev `data/feed-alerts-dev.json`): on/off and the pauses; `feeds.alerts.to` (empty, env `RAILRADIUS_ALERTS_TO`): recipient, nothing is mailed without one; `feeds.alerts.from` (env `RAILRADIUS_ALERTS_FROM`, default the SMTP login)
- `spring.mail.*`: SMTP server of the alert mail. Port 587 with STARTTLS and auth and 10 s timeouts are preset; `host`, `username` and `password` (env `SPRING_MAIL_HOST`, `SPRING_MAIL_USERNAME`, `SPRING_MAIL_PASSWORD`) go in `backend/config/application.yml` or env vars, never in git. Without a host nothing is mailed
- `cache.predictive-enabled` (true), `cache.predictive-max-transfers` (5), `cache.raw-max-entries` (30)
- `search.gate.permits` (2): searches that run at once; `search.gate.max-queued` (6): searches that may wait for a permit before the next one is turned away
- `search.deadline-ms` (30000): a search running longer than this, from when it got its permit, stops and stores nothing (S33). The stream timeout follows from it: 2.5 × (⌈`max-queued` / `permits`⌉ + 1) × this (`SearchAdmission.longestWait`), 5 minutes at the defaults
- `search.rate-limit.capacity` (200), `search.rate-limit.refill-per-second` (1): the search budget per client key (IPv4 address or IPv6 /64); the capacity must cover the biggest search's cost (87: 5 transfers at the 360-min max wait; checked at startup)
- `admin.token` (empty, env `RAILRADIUS_ADMIN_TOKEN`): shared secret for the admin API and the rate-limit exemption; empty disables both. The live server sets one, since the feed alerts are managed in the admin panel (`docs/HOSTING.md`)
- `server.compression` (on, `application/wasm` only): `search.wasm` goes out gzipped, 0.30 instead of 0.86 MB (#12); nothing else is compressed by the app, and the browser data file is gzipped already
- `server.forward-headers-strategy` (`none`, env `RAILRADIUS_FORWARD_HEADERS_STRATEGY`): set `native` behind a reverse proxy, so the rate limit sees the client's IP from `X-Forwarded-For` instead of the proxy's

`application-dev.yml` overrides the GTFS directory, store file and alert settings file, sets `auto-load-from-files: true` and `feeds.sources: austria,hungary,slovakia`, turns predictive warming off and defaults `admin.token` to `dev`. `application-mini.yml` does the same for `data/gtfs-mini/` (store `data/gtfs-mini-store.bin`, browser data `data/browser-data-mini`, alert settings `data/feed-alerts-mini.json`, `feeds.sources` the 12 feeds `scripts/mini-data.sh` zips).
